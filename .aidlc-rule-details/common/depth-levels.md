# 適応的な深度

**目的**: AI-DLC が問題の複雑さに応じて詳細レベルをどのように適応させるかを説明する

## 基本原則

**ステージが実行される際には、定義されたすべての成果物が作成される。「深度 (depth)」とは、それらの成果物内の詳細とリゴアのレベルを指し、問題の複雑さに応じて適応する。**

## ステージ選択と詳細レベル

### ステージ選択 (二値)
- **ワークフロープランニング (Workflow Planning)** が決定する: 各ステージを実行する (EXECUTE) かスキップする (SKIP) か
- **実行する (EXECUTE) 場合**: ステージが実行され、定義されたすべての成果物が作成される
- **スキップする (SKIP) 場合**: ステージはまったく実行されない

### 詳細レベル (適応的)
- **シンプルな問題**: 本質的な詳細を含む簡潔な成果物
- **複雑な問題**: 広範な詳細を含む包括的な成果物
- **モデルが判断する**: 規範的なルールではなく、問題の特性に基づいて

## 詳細レベルに影響する要因

モデルは適切な詳細レベルを決定する際に以下の要因を考慮する:

1. **リクエストの明確さ**: ユーザーのリクエストはどれほど明確で完全か？
2. **問題の複雑さ**: 解決策の空間はどれほど複雑か？
3. **スコープ**: 単一ファイル、コンポーネント、複数コンポーネント、またはシステム全体か？
4. **リスクレベル**: エラーや欠落の影響はどの程度か？
5. **利用可能なコンテキスト**: グリーンフィールド (Greenfield) vs ブラウンフィールド (Brownfield)、既存のドキュメント
6. **ユーザーの希望**: ユーザーが簡潔さまたは詳細さへの好みを表明しているか？

## 例: 要件分析 (Requirements Analysis) の成果物

**すべてのシナリオで同じ成果物が作成される**:
- `requirement-verification-questions.md` (必要な場合)
- `requirements.md`

**注意**: ユーザーの最初のリクエストは `audit.md` に記録される (個別の user-intent.md は不要)

**詳細レベルは複雑さによって変わる**:

### シンプルなシナリオ (バグ修正)
- **requirement-verification-questions.md**: 必要な確認質問
- **requirements.md**: 簡潔な機能要件、最小限のセクション

### 複雑なシナリオ (システム移行)
- **requirement-verification-questions.md**: 複数ラウンド、10以上の質問
- **requirements.md**: 包括的な機能要件と非機能要件、トレーサビリティ、受け入れ基準

## 例: アプリケーション設計 (Application Design) の成果物

**すべてのシナリオで同じ成果物が作成される**:
- `application-design.md`
- `component-diagram.md`

**詳細レベルは複雑さによって変わる**:

### シンプルなシナリオ (単一コンポーネント)
- **application-design.md**: 基本的なコンポーネントの説明、主要なメソッド
- **component-diagram.md**: 本質的な関係を持つシンプルなダイアグラム

### 複雑なシナリオ (マルチコンポーネントシステム)
- **application-design.md**: 詳細なコンポーネントの責務、シグネチャを含むすべてのメソッド、設計パターン、検討した代替案
- **component-diagram.md**: すべての関係、データフロー、統合ポイントを含む包括的なダイアグラム

## モデルへの指針

**「その問題に必要な詳細をちょうど作成すること — それ以上でも、それ以下でもなく。」**

- シンプルな問題に不必要な詳細を加えて人為的に膨らませない
- 重要な詳細を省いて複雑な問題を軽視しない
- 問題の特性が詳細レベルを自然に決定するようにする
- ステージが実行された際はすべての必要な成果物を常に作成する
