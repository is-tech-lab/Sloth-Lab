# 質問フォーマットガイド

## 必須 (MANDATORY): すべての質問はこのフォーマットに従うこと

### ルール: チャットで質問してはならない
**重要 (CRITICAL)**: チャット内で直接質問することは絶対に禁止 (NEVER) です。すべての質問は専用の質問ファイルに配置しなければなりません。

### 質問ファイルのフォーマット

#### ファイル命名規則
- わかりやすい名前を使用する: `{phase-name}-questions.md`
- 例:
  - `classification-questions.md`
  - `requirements-questions.md`
  - `story-planning-questions.md`
  - `design-questions.md`

#### 質問の構造
すべての質問には、意味のある選択肢と最後の選択肢として「その他 (Other)」を含めること:

```markdown
## 質問 [番号]
[明確で具体的な質問文]

A) [最初の意味ある選択肢]
B) [2番目の意味ある選択肢]
[...必要に応じて追加の選択肢...]
X) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: 
```

**重要 (CRITICAL)**: 
- 「その他 (Other)」はすべての質問で**最後の選択肢**として必須 (MANDATORY) です
- 意味のある選択肢のみを含めること — 枠を埋めるために選択肢を作り上げないこと
- 意味を成す範囲で選択肢の数は自由 (最低 2つ + その他)

### 完全な例

```markdown
# 要件確認の質問

以下の質問に回答して要件の明確化にご協力ください。

## 質問 1
主なユーザー認証方式は何ですか？

A) ユーザー名とパスワード
B) ソーシャルメディアログイン (Google, Facebook)
C) シングルサインオン (SSO)
D) 多要素認証
E) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: 

## 質問 2
これは Web アプリケーションですか、モバイルアプリケーションですか？

A) Web アプリケーション
B) モバイルアプリケーション
C) Web とモバイルの両方
D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: 

## 質問 3
これは新規プロジェクトですか、既存のコードベースですか？

A) 新規プロジェクト (グリーンフィールド (greenfield))
B) 既存のコードベース (ブラウンフィールド (brownfield))
C) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: 
```

### ユーザーの回答フォーマット
ユーザーは `[Answer]:` タグの後にアルファベットの選択肢を記入して回答します:

```markdown
## 質問 1
主なユーザー認証方式は何ですか？

A) ユーザー名とパスワード
B) ソーシャルメディアログイン (Google, Facebook)
C) シングルサインオン (SSO)
D) 多要素認証

[Answer]: C
```

### ユーザーの回答を読み取る
ユーザーが完了を確認した後:
1. 質問ファイルを読み込む
2. `[Answer]:` タグ以降の回答を抽出する
3. すべての質問が回答されているかを検証する
4. 回答に基づいて分析を進める

### 複数選択形式のガイドライン

#### 選択肢の数
- 最小: 意味のある選択肢 2つ + 「その他 (Other)」(A, B, C)
- 典型的: 意味のある選択肢 3〜4つ + 「その他 (Other)」(A, B, C, D, E)
- 最大: 意味のある選択肢 5つ + 「その他 (Other)」(A, B, C, D, E, F)
- **重要 (CRITICAL)**: 枠を埋めるために選択肢を作り上げないこと — 意味のある選択肢のみを含めること

#### 選択肢の品質
- 選択肢は相互に排他的にする
- 最も一般的なシナリオをカバーする
- 意味のある現実的な選択肢のみを含める
- **「その他 (Other)」を常に最後の選択肢として含める** (必須 (MANDATORY))
- 具体的で明確にする
- **A, B, C, D の枠を埋めるために選択肢を作り上げないこと**

#### 良い例:
```markdown
## 質問 5
使用するデータベース技術は何ですか？

A) リレーショナル (PostgreSQL, MySQL)
B) NoSQL ドキュメント (MongoDB, DynamoDB)
C) NoSQL キーバリュー (Redis, Memcached)
D) グラフデータベース (Neo4j, Neptune)
E) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: 
```

#### 悪い例 (避けること):
```markdown
## 質問 5
どのデータベースを使いますか？

A) はい
B) いいえ
C) たぶん

[Answer]: 
```

### ワークフローへの統合

#### ステップ 1: 質問ファイルを作成する
```markdown
aidlc-docs/{phase-name}-questions.md にすべての質問を記載して作成する
```

#### ステップ 2: ユーザーに通知する
```
"[X] 個の質問を記載した {phase-name}-questions.md を作成しました。
[Answer]: タグの後にアルファベットの選択肢を記入して各質問に回答してください。
どの選択肢も当てはまらない場合は最後の選択肢 (Other) を選び、希望を記述してください。完了したらお知らせください。"
```

#### ステップ 3: 確認を待つ
ユーザーが「完了」「終わった」「できた」などに相当する言葉を言うまで待つ。

#### ステップ 4: 読み込みと分析
```
aidlc-docs/{phase-name}-questions.md を読み込む
すべての回答を抽出する
完全性を検証する
分析を進める
```

### エラー処理

#### 回答が欠けている場合
`[Answer]:` タグが空の場合:
```
"質問 [X] が回答されていないようです。先に進む前に、すべての質問のアルファベット選択肢を使って回答してください。"
```

#### 無効な回答の場合
回答が有効なアルファベット選択肢でない場合:
```
"質問 [X] の回答 '[answer]' は無効です。
質問に記載されたアルファベット選択肢のみを使用してください。"
```

#### 曖昧な回答の場合
ユーザーが文字選択の代わりに説明文を記述した場合:
```
"質問 [X] について、回答に最も近いアルファベット選択肢を記入してください。
どれにも当てはまらない場合は「Other」を選択し、[Answer]: タグの後に説明を追記してください。"
```

### 矛盾と曖昧さの検出

**必須 (MANDATORY)**: ユーザーの回答を読み込んだ後、必ず矛盾と曖昧さを確認しなければならない。

#### 矛盾の検出
論理的に一貫性のない回答を探す:
- スコープの不一致: 「バグ修正」なのに「コードベース全体に影響する」
- リスクの不一致: 「低リスク」なのに「破壊的変更」
- タイムラインの不一致: 「クイックフィックス」なのに「複数のサブシステム」
- 影響の不一致: 「単一コンポーネント」なのに「大規模なアーキテクチャ変更」

#### 曖昧さの検出
不明確または境界線上の回答を探す:
- 複数の分類に当てはまる可能性がある回答
- 具体性に欠ける回答
- 複数の質問にまたがる矛盾する指標

#### 確認質問の作成
矛盾または曖昧さが検出された場合:

1. **確認ファイルを作成する**: `{phase-name}-clarification-questions.md`
2. **問題を説明する**: 検出された矛盾/曖昧さを明確に述べる
3. **的を絞った質問をする**: 複数選択形式で問題を解決するための質問を行う
4. **元の質問を参照する**: どの質問に矛盾した回答があったかを示す

**例**:
```markdown
# [フェーズ名] 確認質問

回答に矛盾が検出されたため、確認が必要です:

## 矛盾 1: [簡潔な説明]
「[回答 A]」(Q[X]:[選択肢]) と「[回答 B]」(Q[Y]:[選択肢]) の両方を選択しています。
これらの回答は [理由] のために矛盾しています。

### 確認質問 1
[矛盾を解消するための具体的な質問]

A) [最初の回答に寄り添う選択肢]
B) [2番目の回答に寄り添う選択肢]
C) [中間点となる選択肢]
D) [質問を再構成する選択肢]

[Answer]: 

## 曖昧さ 1: [簡潔な説明]
Q[X] への回答「[回答]」は [理由] のため曖昧です。

### 確認質問 2
[曖昧さを解消するための具体的な質問]

A) [明確な選択肢 1]
B) [明確な選択肢 2]
C) [明確な選択肢 3]
D) [明確な選択肢 4]

[Answer]: 
```

#### 確認のワークフロー

1. **検出**: すべての回答を矛盾/曖昧さについて分析する
2. **作成**: 問題が見つかった場合は確認質問ファイルを生成する
3. **通知**: 問題と確認ファイルについてユーザーに伝える
4. **待機**: ユーザーが確認を提供するまで進めない
5. **再検証**: 確認後、一貫性を再度確認する
6. **進行**: すべての矛盾が解消されてから先に進む

#### ユーザーへのメッセージ例
```
"回答に2つの矛盾が検出されました:

1. バグ修正のスコープとコードベースへの影響 (Q1 vs Q2)
2. 低リスクと破壊的変更 (Q7 vs Q4)

これらを解消するための2つの質問を classification-clarification-questions.md に作成しました。
分類を進める前に、これらの確認質問に回答してください。"
```

### ベストプラクティス

1. **具体的に**: 質問は明確で曖昧さがないようにする
2. **包括的に**: 必要な情報をすべてカバーする
3. **簡潔に**: 質問は1つのトピックに絞る
4. **実用的に**: 選択肢は現実的で実行可能なものにする
5. **一貫して**: すべての質問ファイルで同一のフォーマットを使用する

## まとめ

**覚えておくこと**: 
- ✅ 常に質問ファイルを作成する
- ✅ 常に複数選択形式を使用する
- ✅ **「その他 (Other)」を常に最後の選択肢として含める (必須 (MANDATORY))**
- ✅ 意味のある選択肢のみを含める — 枠を埋めるために作り上げない
- ✅ 常に `[Answer]:` タグを使用する
- ✅ 常にユーザーの完了を待つ
- ✅ 常に回答の矛盾を検証する
- ✅ 必要に応じて常に確認ファイルを作成する
- ✅ 常に矛盾を解消してから進む
- ❌ チャットで質問してはならない (禁止 (NEVER))
- ❌ A, B, C, D の枠を埋めるために選択肢を作り上げてはならない
- ❌ 回答なしに進んではならない
- ❌ 未解消の矛盾があるまま進んではならない
- ❌ 曖昧な回答について仮定を立ててはならない
