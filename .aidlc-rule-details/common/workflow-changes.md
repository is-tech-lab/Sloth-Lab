# ワークフロー途中の変更とステージ管理

## 概要

ユーザーはワークフロー中に実行計画やステージの実行に対する変更を要求することがある。このドキュメントでは、それらの要求を安全かつ効果的に処理するためのガイダンスを提供する。

---

## ワークフロー途中の変更の種類

### 1. スキップしたステージの追加

**シナリオ**: ユーザーが元々スキップされたステージを追加したい

**例**: 「やっぱり、そのステージをスキップしたけどユーザーストーリーを追加したい」

**処理方法**:
1. **要求を確認する**: 「ユーザーストーリー (User Stories) ステージを追加しますか？これによりユーザーストーリーとペルソナが作成されます。確認しますか？」
2. **依存関係を確認する**: すべての前提ステージが完了していることを確認する
3. **実行計画を更新する**: 理由を記載して `execution-plan.md` にステージを追加する
4. **状態を更新する**: `aidlc-state.md` でステージを「PENDING」としてマークする
5. **ステージを実行する**: 通常のステージ実行プロセスに従う
6. **変更を記録する**: タイムスタンプと理由を記載して `audit.md` に記録する

**考慮事項**:
- 新しい成果物の恩恵を受ける可能性がある後のステージを更新する必要がある場合がある
- 新しい情報を組み込むために既存の成果物を修正する必要がある場合がある
- タイムラインが延長される

---

### 2. 計画されたステージのスキップ

**シナリオ**: ユーザーが実行予定のステージをスキップしたい

**例**: 「NFR設計 (NFR Design) ステージは今はスキップしましょう」

**処理方法**:
1. **要求を確認する**: 「NFR設計 (NFR Design) をスキップしますか？これにより NFR パターンや論理コンポーネントが組み込まれなくなります。確認しますか？」
2. **影響について警告する**: 何が欠けるか、およびその潜在的な影響を説明する
3. **明示的な確認を得る**: ユーザーは影響を理解した上で明示的に確認しなければならない
4. **実行計画を更新する**: 理由を記載してステージを「SKIPPED」としてマークする
5. **状態を更新する**: `aidlc-state.md` でステージを「SKIPPED」としてマークする
6. **後のステージを調整する**: 後のステージで手動設定が必要になる場合があることに注記する
7. **変更を記録する**: タイムスタンプと理由を記載して `audit.md` に記録する

**考慮事項**:
- 後のステージが失敗するか手動介入が必要になる場合がある
- ユーザーは欠けている成果物の責任を受け入れる
- 必要に応じて後で追加できる

---

### 3. 現在のステージの再実行

**シナリオ**: ユーザーが現在のステージの結果に満足せず、やり直したい

**例**: 「このユーザーストーリーは気に入らない。最初からやり直せますか？」

**処理方法**:
1. **懸念を理解する**: 「ストーリーの何を変えたいですか？」
2. **選択肢を提示する**:
   - **選択肢 A**: 既存の成果物を修正する (より速く、一部の作業を保持)
   - **選択肢 B**: 完全な再実行 (クリーンスレート、より多くの時間)
3. **再実行を選択した場合**:
   - 既存の成果物をアーカイブする: `{artifact}.backup.{timestamp}`
   - 計画ファイルのステージのチェックボックスをリセットする
   - `aidlc-state.md` でステージを「IN PROGRESS」としてマークする
   - ステージの完了ステータスをクリアする
   - 最初から再実行する
4. **変更を記録する**: 再実行の理由と変更内容を記録する

**考慮事項**:
- 既存の作業は失われる (ただしバックアップされる)
- 依存するステージをやり直す必要がある場合がある
- タイムラインが延長される

---

### 4. 前のステージの再実行

**シナリオ**: ユーザーが完了したステージに戻り、やり直したい

**例**: 「以前に行ったアーキテクチャ上の意思決定を変更したい」

**処理方法**:
1. **影響を評価する**: 再実行するステージに依存するすべてのステージを特定する
2. **ユーザーに警告する**: 「アプリケーション設計 (Application Design) を再実行すると、次のものをやり直す必要があります: ユニット生成 (Units Generation)、ユニットごとの設計 (すべてのユニット)、コード生成 (Code Generation)。確認しますか？」
3. **明示的な確認を得る**: ユーザーは完全な影響を理解しなければならない
4. **確認された場合**:
   - 影響を受けるすべての成果物をアーカイブする
   - `aidlc-state.md` で影響を受けるすべてのステージをリセットする
   - 影響を受けるすべての計画ファイルのチェックボックスをクリアする
   - 再実行するステージに戻る
   - そこから先を再実行する
5. **変更を記録する**: 完全な影響と再実行の理由を記録する

**考慮事項**:
- 大幅な再作業が必要
- 依存するすべてのステージをやり直さなければならない
- タイムラインが大幅に延長される
- 再実行よりも修正の方が適切かどうかを検討する

---

### 5. ステージの深度レベルの変更

**シナリオ**: ユーザーが現在または今後のステージの深度レベルを変更したい

**例**: 「標準的な要件分析ではなく、包括的な要件分析を行いましょう」

**処理方法**:
1. **要求を確認する**: 「要件分析 (Requirements Analysis) を標準 (Standard) から包括的 (Comprehensive) な深度に変更しますか？より徹底的になりますが、時間がかかります。確認しますか？」
2. **実行計画を更新する**: `workflow-planning.md` の深度レベルを変更する
3. **アプローチを調整する**: ステージに対して包括的な深度のガイドラインに従う
4. **見積もりを更新する**: 新しいタイムライン見積もりをユーザーに通知する
5. **変更を記録する**: 深度の変更と理由を記録する

**考慮事項**:
- 深度が高い = 時間はかかるが品質が高い
- 深度が低い = 速いが詳細を見落とす可能性がある
- ステージの完了前または進行中にのみ変更できる (完了後は不可)

---

### 6. ワークフローの一時停止

**シナリオ**: ユーザーが一時停止して後で再開する必要がある

**例**: 「今日はここで終わりにして、明日続けたい」

**処理方法**:
1. **現在のステップを完了する**: 可能であれば進行中の現在のステップを終える
2. **チェックボックスを更新する**: 完了したすべてのステップに [x] をマークする
3. **状態を更新する**: `aidlc-state.md` が現在のステータスを反映していることを確認する
4. **一時停止を記録する**: `audit.md` に一時停止ポイントを記録する
5. **再開の手順を提供する**: 「戻ってきたとき、既存のプロジェクトを検出して続きから再開を提案します: [現在のステージ、現在のステップ]」

**再開時**:
1. **既存プロジェクトを検出する**: `aidlc-state.md` を確認する
2. **コンテキストを読み込む**: 完了したステージからすべての成果物を読み込む
3. **ステータスを表示する**: 現在のステージと次のステップを表示する
4. **選択肢を提示する**: 前回の続きから再開するか、前の作業を確認するか
5. **再開を記録する**: `audit.md` に再開ポイントを記録する

---

### 7. アーキテクチャ上の意思決定の変更

**シナリオ**: ユーザーがモノリスからマイクロサービスへの変更 (またはその逆) を希望する

**例**: 「やっぱり、モノリスではなくマイクロサービスにしましょう」

**処理方法**:
1. **現在の進捗を評価する**: ワークフローのどこまで進んでいるかを判断する
2. **影響を説明する**: 
   - ユニット生成 (Units Generation) 前の場合: 影響は最小限、意思決定を更新するだけ
   - ユニット生成 (Units Generation) 後の場合: ユニット生成 (Units Generation) とすべてのユニットごとの設計をやり直す必要がある
   - コード生成 (Code Generation) 後の場合: 大幅な再作業が必要
3. **アプローチを推奨する**:
   - ワークフローの早い段階: アプリケーション設計 (Application Design) ステージから再開する
   - ワークフローの遅い段階: 修正が可能か、再実行するかを検討する
4. **確認を得る**: ユーザーは変更の完全なスコープを理解しなければならない
5. **変更を実行する**: 影響を受けるステージの再実行手順に従う

**考慮事項**:
- アーキテクチャの変更は連鎖的な影響を持つ
- ワークフローの早い段階 = 変更が容易
- ワークフローの遅い段階 = コストと便益を考慮する

---

### 8. ユニットの追加/削除

**シナリオ**: ユニット生成 (Units Generation) 後にユーザーがユニットを追加または削除したい

**例**: 「Payment ユニットを Payment と Billing に分割する必要がある」

**処理方法**:
1. **影響を評価する**: 設計/コードが完了しているユニットを特定する
2. **影響を説明する**:
   - ユニットの追加: 新しいユニットに対して完全な設計とコードを行う必要がある
   - ユニットの削除: 機能を他のユニットに再分配する必要がある
   - ユニットの分割: 結果として生まれる両方のユニットの設計とコードをやり直す必要がある
3. **ユニットの成果物を更新する**:
   - `unit-of-work.md` を修正する
   - `unit-of-work-dependency.md` を更新する
   - `unit-of-work-story-map.md` を修正する
4. **影響を受けるユニットをリセットする**: 影響を受けるユニットを再設計が必要とマークする
5. **変更を実行する**: 影響を受けるユニットに対して通常のユニット設計とコードのプロセスに従う

**考慮事項**:
- それらのユニットのすべての下流ステージに影響する
- 依存関係が変わった場合、他のユニットにも影響する可能性がある
- タイムラインへの影響は影響を受けるユニットの数によって異なる

## 変更処理の一般ガイドライン

### 変更を行う前に

1. **要求を理解する**: ユーザーが何を、なぜ変更したいかについて確認質問を行う
2. **影響を評価する**: 影響を受けるすべてのステージ、成果物、依存関係を特定する
3. **影響を説明する**: 何をやり直す必要があるか、およびタイムラインへの影響を明確に伝える
4. **代替案を提示する**: 再実行よりも修正の方が適切な場合がある
5. **明示的な確認を得る**: ユーザーは影響を理解して受け入れなければならない

### 変更中に

1. **既存の作業をアーカイブする**: 破壊的な変更を行う前に常にバックアップする
2. **すべての追跡を更新する**: `aidlc-state.md`、計画ファイル、`audit.md` を同期させる
3. **進捗を伝達する**: 何が起きているかをユーザーに知らせる
4. **変更を検証する**: 変更がすべての成果物にわたって一貫していることを確認する
5. **継続性をテストする**: 変更後にワークフローがスムーズに続行できることを確認する

### 変更後に

1. **一貫性を確認する**: すべての成果物が変更と整合していることを確認する
2. **ドキュメントを更新する**: すべての参照が更新されていることを確認する
3. **完全に記録する**: `audit.md` に完全な変更履歴を記録する
4. **ユーザーと確認する**: 変更がユーザーの期待を満たしていることを確認する
5. **ワークフローを再開する**: 新しい状態から通常の実行を続ける

## 変更要求の意思決定ツリー

```
User requests change
    |
    ├─ Is it current stage?
    |   ├─ Yes: Can modify or restart current stage
    |   └─ No: Go to next question
    |
    ├─ Is it a completed stage?
    |   ├─ Yes: Assess impact on dependent stages
    |   |   ├─ Low impact: Modify and update dependents
    |   |   └─ High impact: Recommend restart from that stage
    |   └─ No: Go to next question
    |
    ├─ Is it adding a skipped stage?
    |   ├─ Yes: Check prerequisites, add to plan, execute
    |   └─ No: Go to next question
    |
    ├─ Is it skipping a planned stage?
    |   ├─ Yes: Warn about impact, get confirmation, skip
    |   └─ No: Go to next question
    |
    └─ Is it changing depth level?
        ├─ Yes: Update plan, adjust approach
        └─ No: Clarify request with user
```

## ベストプラクティス

1. **常に確認する**: 明示的なユーザーの確認なしに破壊的な変更を行ってはならない (禁止 (NEVER))
2. **影響を説明する**: ユーザーは決定前に影響を理解する必要がある
3. **選択肢を提示する**: 変更を処理するのに複数の方法がある場合がある
4. **先にアーカイブする**: 破壊的な変更を行う前に常にバックアップする
5. **すべてを更新する**: すべての追跡ファイルを同期させる
6. **徹底的に記録する**: 監査証跡のためにすべての変更を記録する
7. **変更後に検証する**: ワークフローがスムーズに続行できることを確認する
8. **柔軟に対応する**: ワークフローはユーザーのニーズに適応すべきであり、硬直したプロセスを強制してはならない
