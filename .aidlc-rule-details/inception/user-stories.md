# ユーザーストーリー (User Stories) - 詳細ステップ

## 目的
**要件をユーザー中心のストーリーと受け入れ基準に変換する**

ユーザーストーリー (User Stories) の焦点:
- ビジネス要件をユーザー中心のナラティブに変換する
- 各ストーリーに明確な受け入れ基準を定義する
- 異なるステークホルダータイプを表すユーザーペルソナを作成する
- チーム全体での共通理解を確立する
- 実装のためのテスト可能な仕様を提供する

## 前提条件
- ワークスペース検出 (Workspace Detection) が完了していること
- 要件分析 (Requirements Analysis) を推奨する（利用可能な場合は要件を参照できる）
- ワークフロープランニング (Workflow Planning) でユーザーストーリー (User Stories) ステージを実行すると示されていること

## インテリジェント評価ガイドライン

**ユーザーストーリーを実行するタイミング**: 進める前にこの強化された評価を使用する:

### 高優先度実行（常時実行 (ALWAYS Execute)）
- **新規ユーザー機能 (New User Features)**: ユーザーが直接インタラクションする新機能
- **ユーザーエクスペリエンスの変更 (User Experience Changes)**: 既存のユーザーワークフローやインターフェースの変更
- **マルチペルソナシステム (Multi-Persona Systems)**: 異なるタイプのユーザーにサービスを提供するアプリケーション
- **顧客向け API (Customer-Facing APIs)**: 外部ユーザーやシステムが利用するサービス
- **複雑なビジネスロジック (Complex Business Logic)**: 複数のシナリオやビジネスルールを持つ要件
- **クロスチームプロジェクト (Cross-Team Projects)**: 複数チームにまたがる共通理解が必要な作業

### 中優先度実行（複雑性を評価する）
- **バックエンドのユーザー影響 (Backend User Impact)**: ユーザーエクスペリエンスに間接的に影響する内部変更
- **パフォーマンス改善 (Performance Improvements)**: ユーザーに見える改善効果をもたらす機能強化
- **統合作業 (Integration Work)**: ユーザーワークフローに影響するシステム連携
- **データ変更 (Data Changes)**: ユーザーデータ、レポート、分析に影響する変更
- **セキュリティ強化 (Security Enhancements)**: ユーザー認証や権限に影響する変更

### 複雑性評価要素
中優先度ケースでは、以下のいずれかに該当する場合にユーザーストーリーを実行する:
- **スコープ (Scope)**: 変更が複数のコンポーネントやユーザーのタッチポイントにまたがる
- **曖昧さ (Ambiguity)**: 要件にストーリーが明確化できる不明確な点がある
- **リスク (Risk)**: ビジネスへの影響が高い、または誤解の可能性がある
- **ステークホルダー (Stakeholders)**: 要件に複数のビジネスステークホルダーが関与している
- **テスト (Testing)**: ユーザー受け入れテストが必要になる
- **選択肢 (Options)**: 有効な実装アプローチが複数存在する

### シンプルなケースでのみスキップする
- **純粋なリファクタリング (Pure Refactoring)**: ユーザーへの影響がゼロの内部コード改善
- **孤立したバグ修正 (Isolated Bug Fixes)**: 明確なスコープを持つシンプルで明確な修正
- **インフラのみの変更 (Infrastructure Only)**: ユーザー向け効果のない変更
- **開発者ツール (Developer Tooling)**: ビルドプロセス、CI/CD、または開発環境の変更
- **ドキュメント (Documentation)**: 機能に影響しない更新

### デフォルトの決定ルール
**迷った場合は、ユーザーストーリーを含め、確認質問をする。** 適切な確認とともに包括的なストーリーを作成するオーバーヘッドは、通常、以下のメリットにより上回られる:
- より明確な要件理解
- より良いチームの整合性
- 改善されたテスト基準
- ステークホルダーとのコミュニケーション強化
- 実装リスクの低減
- 開発中のコストのかかる変更の削減
- より良いユーザーエクスペリエンスの成果

# パート 1: プランニング

## ステップ 1: ユーザーストーリーの必要性を検証する（必須 (MANDATORY)）

**重要 (CRITICAL)**: ユーザーストーリーに進む前に、この評価を実施する:

### 評価プロセス
1. **リクエストコンテキストを分析する**:
   - 元のユーザーリクエストと要件をレビューする
   - ユーザー向けの変更と内部のみの変更を識別する
   - 作業の複雑性とスコープを評価する
   - ビジネスステークホルダーの関与を評価する

2. **評価基準を適用する**:
   - 高優先度の指標を確認する（常時実行）
   - 中優先度の要素を評価する（複雑性に基づく決定）
   - スキップすべきシンプルなケースでないことを確認する

3. **評価決定を文書化する**:
   - `aidlc-docs/inception/plans/user-stories-assessment.md` を作成する
   - このリクエストにユーザーストーリーが価値をもたらす理由を記載する
   - 適用される具体的な評価基準を参照する
   - 期待されるメリット（明確性、テスト、ステークホルダーの整合性）を説明する

4. **正当化された場合にのみ進める**:
   - ユーザーストーリーはプロジェクトに明確な価値を追加する必要がある
   - 評価はオーバーヘッドを上回る具体的なメリットを示す必要がある
   - 決定はプロジェクトのステークホルダーに対して説明できるものでなければならない

### 評価ドキュメントテンプレート
```markdown
# User Stories Assessment

## Request Analysis
- **Original Request**: [Brief summary]
- **User Impact**: [Direct/Indirect/None]
- **Complexity Level**: [Simple/Medium/Complex]
- **Stakeholders**: [List involved parties]

## Assessment Criteria Met
- [ ] High Priority: [List applicable criteria]
- [ ] Medium Priority: [List applicable criteria with complexity justification]
- [ ] Benefits: [Expected value from user stories]

## Decision
**Execute User Stories**: [Yes/No]
**Reasoning**: [Detailed justification]

## Expected Outcomes
- [List specific benefits user stories will provide]
- [How stories will improve project success]
```

## ステップ 2: ストーリー計画の作成
- プロダクトオーナーの役割を担う
- ストーリー開発のためのステップバイステップの実行チェックリストを含む包括的な計画を生成する
- 各ステップとサブステップにチェックボックス [] を設ける
- 要件をユーザーストーリーに変換するための方法論とアプローチに焦点を当てる

## ステップ 3: コンテキストに適した質問の生成
**指令**: 要件とコンテキストを徹底的に分析し、明確化によってストーリーの品質とチームの理解を向上させられる全領域を特定する。包括的なユーザーストーリー開発を確保するために積極的に質問する。

**重要 (CRITICAL)**: ストーリーの品質に影響しうる曖昧さや不足している詳細が少しでもある場合は、デフォルトで質問する。不完全または不明確なストーリーを作成するよりも、多すぎるくらい質問する方が良い。

**質問のフォーマットルールについては `common/question-format-guide.md` を参照**

- `[Answer]:` タグ形式を使用して質問を埋め込む
- 曖昧さ、不足している情報、または明確化が必要な領域について質問する
- ユーザーの入力によってストーリー作成の決定が改善される箇所に質問を生成する
- **迷った場合は質問する** — 過信は質の低いストーリーにつながる

**評価する質問カテゴリー**（すべてのカテゴリーを検討する）:
- **ユーザーペルソナ (User Personas)** — ユーザータイプ、役割、特性、動機について質問する
- **ストーリーの粒度 (Story Granularity)** — 適切な詳細レベル、ストーリーサイズ、分解アプローチについて質問する
- **ストーリー形式 (Story Format)** — 形式の好み、テンプレートの使用、ドキュメント標準について質問する
- **分解アプローチ (Breakdown Approach)** — 整理方法、優先順位付け、グループ化戦略について質問する
- **受け入れ基準 (Acceptance Criteria)** — 詳細レベル、形式、テストアプローチ、検証方法について質問する
- **ユーザージャーニー (User Journeys)** — ユーザーワークフロー、インタラクションパターン、エクスペリエンスフローについて質問する
- **ビジネスコンテキスト (Business Context)** — ビジネス目標、成功指標、ステークホルダーのニーズについて質問する
- **技術的制約 (Technical Constraints)** — 技術的な制限、統合要件、システム境界について質問する

## ステップ 4: 必須ストーリー成果物を計画に含める
- 以下の必須成果物を**常に**ストーリー計画に含める:
  - [ ] INVEST 基準に従ったユーザーストーリーを含む stories.md を生成する
  - [ ] ユーザーアーキタイプと特性を含む personas.md を生成する
  - [ ] ストーリーが独立 (Independent)、交渉可能 (Negotiable)、価値ある (Valuable)、見積もり可能 (Estimable)、小さい (Small)、テスト可能 (Testable) であることを確認する
  - [ ] 各ストーリーの受け入れ基準を含める
  - [ ] ペルソナを関連するユーザーストーリーにマッピングする

## ステップ 5: ストーリーオプションの提示
- 計画ドキュメントにストーリー分解の異なるアプローチを含める:
  - **ユーザージャーニーベース (User Journey-Based)**: ストーリーはユーザーワークフローとインタラクションに沿っている
  - **機能ベース (Feature-Based)**: システムの機能と能力を中心に整理されたストーリー
  - **ペルソナベース (Persona-Based)**: 異なるユーザータイプとそのニーズ別にグループ化されたストーリー
  - **ドメインベース (Domain-Based)**: ビジネスドメインまたはコンテキスト別に整理されたストーリー
  - **エピックベース (Epic-Based)**: サブストーリーを持つ階層的なエピックとして構造化されたストーリー
- 各アプローチのトレードオフとメリットを説明する
- 明確な決定基準を持つハイブリッドアプローチを許容する

## ステップ 6: ストーリー計画の保存
- 埋め込まれた質問を含む完全なストーリー計画を `aidlc-docs/inception/plans/` ディレクトリに保存する
- ファイル名: `story-generation-plan.md`
- ユーザー入力用のすべての `[Answer]:` タグを含める
- 計画が包括的でストーリー開発のすべての側面をカバーしていることを確認する

## ステップ 7: ユーザー入力の要求
- ストーリー計画ドキュメント内のすべての `[Answer]:` タグを直接入力するようユーザーに依頼する
- 監査証跡と意思決定の記録の重要性を強調する
- `[Answer]:` タグの入力方法について明確な指示を提供する
- 次に進む前にすべての質問に回答する必要があることを説明する

## ステップ 8: 回答の収集
- ドキュメント内の `[Answer]:` タグを使用してすべての質問に回答するのをユーザーが完了するのを待つ
- すべての `[Answer]:` タグが完了するまで進まない
- `[Answer]:` タグが空白のまま残っていないことを確認するためにドキュメントをレビューする

## ステップ 9: 回答を分析する（必須 (MANDATORY)）
進める前に、すべてのユーザー回答を以下について注意深くレビューしなければならない:
- **曖昧または不明確な回答**: "〜の混合"、"〜の間のどこか"、"よくわからない"、"次第"、"たぶん"、"おそらく"
- **未定義の基準または用語**: 明確な定義のない概念への参照
- **矛盾した回答**: 互いに矛盾する回答
- **不足している生成詳細**: 実装の具体的な指針がない回答
- **選択肢を組み合わせた回答**: 明確な決定ルールなしに異なるアプローチを混合した回答
- **不完全な説明**: 定義せずに外部要因を参照している回答
- **仮定に基づく回答**: 明示的に述べられていない知識を前提とした回答

## ステップ 10: 必須フォローアップ質問
ステップ 9 の分析で曖昧な回答が見つかった場合は、以下を必ず行う:
- `[Answer]:` タグを使用して別の確認質問ファイルを作成する
- すべての曖昧さが完全に解消されるまで承認に進まない
- **重要 (CRITICAL)**: 徹底的に — すべての不明確な回答に対してフォローアップ質問をする
- 必要なフォローアップの例:
  - "「A と B の混合」と述べていましたが、A と B のどちらを使うかを決める具体的な基準は何ですか？"
  - "「A と B の間のどこか」と述べていましたが、正確な中間アプローチを定義できますか？"
  - "「よくわからない」と述べていましたが、決定に役立つ追加情報は何ですか？"
  - "「複雑さ次第」と述べていましたが、複雑さのレベルと閾値をどのように定義しますか？"
  - "「ハイブリッドアプローチ」を選択しましたが、各手法を使用する具体的なルールは何ですか？"
  - "「おそらく X」と述べていましたが、確実に X になる要因と確実に X にならない要因は何ですか？"
  - "「標準的なプラクティス」と述べていましたが、その標準的なプラクティスとは何か定義できますか？"

## ステップ 11: 実装詳細を避ける
- 優先順位付けや開発タスクではなく、ストーリー作成の方法論に焦点を当てる
- このステージでは技術的な生成について議論しない
- 開発タイムラインやスプリント計画の作成を避ける
- ストーリー構造と形式の決定に焦点を当て続ける

## ステップ 12: 承認プロンプトの記録
- 承認を求める前に、プロンプトをタイムスタンプとともに `aidlc-docs/audit.md` に記録する
- 完全な承認プロンプトテキストを含める
- ISO 8601 タイムスタンプ形式を使用する

## ステップ 13: 計画の明示的な承認を待つ
- ユーザーがストーリーアプローチを明示的に承認するまで進まない
- 承認は明確で曖昧でないものでなければならない
- ユーザーが変更を要求した場合は、計画を更新して承認プロセスを繰り返す

## ステップ 14: 承認レスポンスの記録
- ユーザーの承認レスポンスをタイムスタンプとともに `aidlc-docs/audit.md` に記録する
- 正確なユーザー回答テキストを含める
- 承認ステータスを明確にマークする

# 重要なルール (CRITICAL RULES)

## プランニングフェーズのルール
- **コンテキストに適した質問 (CONTEXT-APPROPRIATE QUESTIONS)**: この特定のコンテキストに関連する質問のみを行う
- **必須回答分析 (MANDATORY ANSWER ANALYSIS)**: 進める前に必ず回答の曖昧さを分析する
- **曖昧さを持って進まない (NO PROCEEDING WITH AMBIGUITY)**: 生成前にすべての曖昧な回答を解消する必要がある
- **明示的な承認が必要 (EXPLICIT APPROVAL REQUIRED)**: 生成を開始する前にユーザーが計画を承認しなければならない

## 生成フェーズのルール
- **ハードコードされたロジックなし (NO HARDCODED LOGIC)**: ストーリー生成計画に書かれていることのみを実行する
- **計画に正確に従う (FOLLOW PLAN EXACTLY)**: ステップのシーケンスから逸脱しない
- **チェックボックスを更新する (UPDATE CHECKBOXES)**: 各ステップ完了後すぐに `[x]` にマークする
- **承認された方法論を使用する (USE APPROVED METHODOLOGY)**: プランニングからのストーリーアプローチに従う
- **完了を検証する (VERIFY COMPLETION)**: 進む前にすべてのストーリー成果物が完成していることを確認する
