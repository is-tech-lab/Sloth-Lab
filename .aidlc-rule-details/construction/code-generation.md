# コード生成 (Code Generation) - 詳細ステップ

## 概要
このステージでは、2つの統合されたパートを通じて各ユニット・オブ・ワーク (unit of work) のコードを生成します:
- **パート1 - 計画**: 明示的なステップを含む詳細なコード生成計画を作成する
- **パート2 - 生成**: 承認済みの計画を実行してコード、テスト、成果物を生成する

**注意**: ブラウンフィールド (Brownfield) プロジェクトの場合、「生成」とは重複ファイルを作成するのではなく、必要に応じて既存ファイルを修正することを意味します。

## 前提条件
- ユニットのユニット設計生成が完了していること
- NFR実装（実行した場合）がユニットについて完了していること
- ユニットのすべての設計成果物が利用可能であること
- ユニットがコード生成の準備ができていること

# パート1: 計画

## ステップ1: ユニットのコンテキストを分析する
- [ ] ユニット設計生成からユニット設計成果物を読み込む
- [ ] ユニットのストーリーマップを読み込み、割り当てられたストーリーを理解する
- [ ] ユニットの依存関係とインターフェースを特定する
- [ ] ユニットがコード生成の準備ができていることを検証する

## ステップ2: 詳細なユニットコード生成計画を作成する
- [ ] `aidlc-docs/aidlc-state.md` からワークスペースのルートとプロジェクトタイプを読み込む
- [ ] コードの配置場所を決定する（構造パターンについては重要ルールを参照）
- [ ] **ブラウンフィールド (Brownfield) のみ**: リバースエンジニアリング (Reverse Engineering) の `code-structure.md` をレビューし、変更する既存ファイルを確認する
- [ ] 正確なパスを文書化する（`aidlc-docs/` は使用禁止）
- [ ] ユニット生成のための明示的なステップを作成する:
  - プロジェクト構造のセットアップ（グリーンフィールド (Greenfield) のみ）
  - ビジネスロジックの生成
  - ビジネスロジックのユニットテスト
  - ビジネスロジックの要約
  - API レイヤーの生成
  - API レイヤーのユニットテスト
  - API レイヤーの要約
  - リポジトリレイヤーの生成
  - リポジトリレイヤーのユニットテスト
  - リポジトリレイヤーの要約
  - フロントエンドコンポーネントの生成（該当する場合）
  - フロントエンドコンポーネントのユニットテスト（該当する場合）
  - フロントエンドコンポーネントの要約（該当する場合）
  - データベースマイグレーションスクリプト（データモデルが存在する場合）
  - ドキュメント生成（APIドキュメント、READMEの更新）
  - デプロイ成果物の生成
- [ ] 各ステップに連番を付ける
- [ ] ストーリーマッピングの参照を含める
- [ ] 各ステップにチェックボックス [] を追加する

## ステップ3: ユニット生成コンテキストを含める
- [ ] このユニットについて以下を含める:
  - このユニットが実装するストーリー
  - 他のユニット/サービスへの依存関係
  - 期待されるインターフェースとコントラクト
  - このユニットが所有するデータベースエンティティ
  - サービス境界と責務

## ステップ4: ユニット計画ドキュメントを作成する
- [ ] 完全な計画を `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md` として保存する
- [ ] ステップ番号を含める（ステップ1、ステップ2など）
- [ ] ユニットのコンテキストと依存関係を含める
- [ ] ストーリーのトレーサビリティを含める
- [ ] 計画がステップバイステップで実行可能であることを確認する
- [ ] この計画がコード生成 (Code Generation) の単一の信頼できる情報源であることを強調する

## ステップ5: ユニット計画を要約する
- [ ] ユニットコード生成計画の要約をユーザーに提供する
- [ ] ユニット生成のアプローチを強調する
- [ ] ステップシーケンスとストーリーカバレッジを説明する
- [ ] ステップの総数と推定スコープを記録する

## ステップ6: 承認プロンプトを記録する
- [ ] 承認を求める前に、タイムスタンプ付きでプロンプトを `aidlc-docs/audit.md` に記録する
- [ ] 完全なユニットコード生成計画への参照を含める
- [ ] ISO 8601 タイムスタンプ形式を使用する

## ステップ7: 明示的な承認を待つ
- [ ] ユーザーがユニットコード生成計画を明示的に承認するまで進めない
- [ ] 承認は計画全体と生成シーケンスをカバーするものであること
- [ ] ユーザーが変更を要求した場合は、計画を更新して承認プロセスを繰り返す

## ステップ8: 承認回答を記録する
- [ ] タイムスタンプ付きでユーザーの承認回答を `aidlc-docs/audit.md` に記録する
- [ ] ユーザーの正確な回答テキストを含める
- [ ] 承認ステータスを明確にマークする

## ステップ9: 進捗を更新する
- [ ] `aidlc-state.md` においてコード生成 (Code Generation) パート1（計画）を完了としてマークする
- [ ] 「現在のステータス」セクションを更新する
- [ ] コード生成 (Code Generation) への移行準備をする

# パート2: 生成

## ステップ10: ユニットコード生成計画を読み込む
- [ ] `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md` から完全な計画を読み込む
- [ ] 次の未完了ステップ（最初の [ ] チェックボックス）を特定する
- [ ] そのステップのコンテキスト（ユニット、依存関係、ストーリー）を読み込む

## ステップ11: 現在のステップを実行する
- [ ] 計画からターゲットディレクトリを確認する（`aidlc-docs/` は使用禁止）
- [ ] **ブラウンフィールド (Brownfield) のみ**: ターゲットファイルが存在するか確認する
- [ ] 現在のステップに記載された内容を正確に生成する:
  - **ファイルが存在する場合**: その場で修正する（`ClassName_modified.java`、`ClassName_new.java` などを作成しない）
  - **ファイルが存在しない場合**: 新しいファイルを作成する
- [ ] 正しい場所に書き込む:
  - **アプリケーションコード**: プロジェクト構造に従ったワークスペースのルート
  - **ドキュメント**: `aidlc-docs/construction/{unit-name}/code/`（マークダウンのみ）
  - **ビルド/設定ファイル**: ワークスペースのルート
- [ ] ユニットのストーリー要件に従う
- [ ] 依存関係とインターフェースを尊重する

## ステップ12: 進捗を更新する
- [ ] ユニットコード生成計画において完了したステップを [x] としてマークする
- [ ] 関連するユニットストーリーの生成が完了したら [x] としてマークする
- [ ] `aidlc-docs/aidlc-state.md` の現在のステータスを更新する
- [ ] **ブラウンフィールド (Brownfield) のみ**: 重複ファイルが作成されていないことを確認する（例: `ClassName.java` と並んで `ClassName_modified.java` がないこと）
- [ ] 生成されたすべての成果物を保存する

## ステップ13: 生成を継続または完了する
- [ ] 残りのステップがある場合は、ステップ10に戻る
- [ ] すべてのステップが完了したら、完了メッセージの提示に進む

## ステップ14: 完了メッセージを提示する
- 完了メッセージを以下の構成で提示する:
     1. **完了アナウンス** (必須): 常に以下で始めること:

```markdown
# 💻 Code Generation Complete - [unit-name]
```

     2. **AI要約** (任意): 構造化された箇条書き要約を提供する
        - **ブラウンフィールド (Brownfield)**: 変更したファイルと作成したファイルを区別する（例: 「• Modified: `src/services/user-service.ts`」「• Created: `src/services/auth-service.ts`」）
        - **グリーンフィールド (Greenfield)**: パス付きで作成したファイルを列挙する（例: 「• Created: `src/services/user-service.ts`」）
        - テスト、ドキュメント、デプロイ成果物をパス付きで列挙する
        - 事実に基づき、ワークフロー指示は含めない
     3. **フォーマットされたワークフローメッセージ** (必須): 常に以下の正確な形式で終わること:

```markdown
> **📋 <u>**REVIEW REQUIRED:**</u>**  
> Please examine the generated code at:
> - **Application Code**: `[actual-workspace-path]`
> - **Documentation**: `aidlc-docs/construction/[unit-name]/code/`



> **🚀 <u>**WHAT'S NEXT?**</u>**
>
> **You may:**
>
> 🔧 **Request Changes** - Ask for modifications to the generated code based on your review  
> ✅ **Continue to Next Stage** - Approve code generation and proceed to **[next-unit/Build & Test]**

---
```

## ステップ15: 明示的な承認を待つ
- ユーザーが生成されたコードを明示的に承認するまで進めない
- 承認は明確かつ曖昧さのないものであること
- ユーザーが変更を要求した場合は、コードを更新して承認プロセスを繰り返す

## ステップ16: 承認を記録し、進捗を更新する
- タイムスタンプ付きで承認を `audit.md` に記録する
- タイムスタンプ付きでユーザーの承認回答を記録する
- `aidlc-state.md` においてこのユニットのコード生成 (Code Generation) ステージを完了としてマークする

## 重要ルール

### コード配置ルール
- **アプリケーションコード**: ワークスペースのルートのみ（`aidlc-docs/` は使用禁止 (NEVER)）
- **ドキュメント**: `aidlc-docs/` のみ（マークダウン要約）
- **ワークスペースルートを読み込む**: コード生成前に `aidlc-state.md` から確認する

**プロジェクトタイプ別の構造パターン**:
- **ブラウンフィールド (Brownfield)**: 既存の構造を使用する（例: `src/main/java/`、`lib/`、`pkg/`）
- **グリーンフィールド (Greenfield) 単一ユニット**: ワークスペースのルートに `src/`、`tests/`、`config/`
- **グリーンフィールド (Greenfield) マルチユニット（マイクロサービス）**: `{unit-name}/src/`、`{unit-name}/tests/`
- **グリーンフィールド (Greenfield) マルチユニット（モノリス）**: `src/{unit-name}/`、`tests/{unit-name}/`

### ブラウンフィールド (Brownfield) ファイル修正ルール
- 生成前にファイルが存在するか確認する
- 存在する場合: その場で修正する（`ClassName_modified.java` のようなコピーを作成しない）
- 存在しない場合: 新しいファイルを作成する
- 生成後に重複ファイルがないことを確認する（ステップ12）

### 計画フェーズのルール
- すべての生成活動に対して明示的な番号付きステップを作成する
- 計画にストーリーのトレーサビリティを含める
- ユニットのコンテキストと依存関係を文書化する
- 生成前にユーザーの明示的な承認を得る

### 生成フェーズのルール
- **ハードコードロジック禁止 (NO HARDCODED LOGIC)**: ユニット計画に記載された内容のみを実行する
- **計画に正確に従う (FOLLOW PLAN EXACTLY)**: ステップシーケンスから逸脱しない
- **チェックボックスを更新する (UPDATE CHECKBOXES)**: 各ステップ完了後すぐに [x] をマークする
- **ストーリートレーサビリティ (STORY TRACEABILITY)**: 機能が実装されたらユニットストーリーを [x] としてマークする
- **依存関係を尊重する (RESPECT DEPENDENCIES)**: ユニットの依存関係が満たされている場合のみ実装する

### オートメーションフレンドリーなコードルール
UI コード（Web、モバイル、デスクトップ）を生成する際は、要素がオートメーションフレンドリーであることを確認する:
- インタラクティブな要素（ボタン、入力フィールド、リンク、フォーム）に `data-testid` 属性を追加する
- 一貫した命名を使用する: `{component}-{element-role}`（例: `login-form-submit-button`、`user-list-search-input`）
- レンダリング間で変化するダイナミックまたは自動生成された ID は避ける
- `data-testid` の値をコード変更を超えて安定させる（要素の目的が変わった場合のみ変更する）

## 完了基準
- 完全なユニットコード生成計画が作成・承認されていること
- ユニットコード生成計画のすべてのステップが [x] としてマークされていること
- すべてのユニットストーリーが計画に従って実装されていること
- すべてのコードとテストが生成されていること（テストはビルドとテスト (Build and Test) フェーズで実行される）
- デプロイ成果物が生成されていること
- 完全なユニットがビルドと検証の準備ができていること
