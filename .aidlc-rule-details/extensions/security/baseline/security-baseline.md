# セキュリティベースライン・ルール (Baseline Security Rules)

## 概要
これらのセキュリティルールは、AI-DLC の全フェーズにわたって適用される**必須** (MANDATORY) の横断的制約です。任意のガイダンスではなく、ハードな制約であり、質問の生成・設計成果物の作成・コード生成・完了メッセージの提示の各ステージで**必ず**適用されなければなりません。

**適用**: 適用対象の各ステージにおいて、モデルはユーザーにステージ完了メッセージを提示する前に、これらのルールへの準拠を検証しなければなりません。

### セキュリティ上のブロッキング指摘事項の取り扱い
**ブロッキングセキュリティ指摘事項**とは以下を意味します：
1. 指摘事項はステージ完了メッセージの「セキュリティ指摘事項」セクションに、SECURITYルールIDと説明とともに**必ず**列挙されなければなりません
2. ステージは、すべてのブロッキング指摘事項が解決されるまで「次のステージに進む」オプションを**提示してはなりません**
3. モデルは「変更を依頼する」オプションのみを提示し、何を変更する必要があるかを明確に説明しなければなりません
4. 指摘事項は、SECURITYルールID・説明・ステージのコンテキストとともに `aidlc-docs/audit.md` に**必ず**記録されなければなりません

SECURITYルールが現在のプロジェクトに適用されない場合（例：データストアが存在しない場合のSECURITY-01）は、コンプライアンスサマリーに **N/A** として記載してください。これはブロッキング指摘事項にはなりません。

### デフォルトの適用
このドキュメント内のすべてのルールは、デフォルトで**ブロッキング**です。いずれかのルールの検証基準が満たされない場合、それはブロッキングセキュリティ指摘事項となり、上記の「ブロッキング指摘事項の取り扱い」に従ってください。

### 検証基準のフォーマット
このドキュメント内の検証項目は、コンプライアンスチェックを記述したプレーンな箇条書きです。これらはステージ計画ファイルで使用される `- [ ]` / `- [x]` の進捗管理チェックボックスとは異なります。各項目はレビュー時に「準拠」または「非準拠」として評価される必要があります。

## ルール SECURITY-01: 保存時および転送時の暗号化 (Encryption at Rest and in Transit)

**ルール**: すべてのデータ永続化ストア（データベース、オブジェクトストレージ、ファイルシステム、キャッシュ、またはこれらに相当するもの）は以下を備えなければなりません：
- マネージドキーサービスまたはカスタマーマネージドキーを使用した保存時の暗号化を有効にすること
- 転送時の暗号化を強制すること（ストアへのすべてのデータ転送に TLS 1.2+ を使用）

**検証**:
- 暗号化設定ブロックなしに定義されたストレージリソースが存在しないこと
- 非暗号化プロトコルを使用したデータベース接続文字列が存在しないこと
- オブジェクトストレージが保存時の暗号化を強制し、ポリシーによって非TLSリクエストを拒否していること
- データベースインスタンスがストレージ暗号化を有効にし、TLS接続を強制していること

---

## ルール SECURITY-02: ネットワーク仲介者のアクセスログ (Access Logging on Network Intermediaries)

**ルール**: 外部トラフィックを処理するすべてのネットワーク向け仲介者はアクセスログを有効にしなければなりません。対象には以下が含まれます：
- ロードバランサー → 永続ストアへのアクセスログ
- APIゲートウェイ → 一元化されたログサービスへの実行ログとアクセスログ
- CDNディストリビューション → 標準ログまたはリアルタイムログ

**検証**:
- アクセスログが有効化されていないロードバランサーリソースが存在しないこと
- アクセスログが設定されていないAPIゲートウェイステージが存在しないこと
- ログ設定なしに定義されたCDNディストリビューションが存在しないこと

---

## ルール SECURITY-03: アプリケーションレベルのログ記録 (Application-Level Logging)

**ルール**: デプロイされたすべてのアプリケーションコンポーネントは構造化ログ基盤を含まなければなりません：
- ロギングフレームワークを**必ず**設定すること
- ログ出力を一元化されたログサービスに**必ず**送信すること
- ログには**必ず**タイムスタンプ、相関ID/リクエストID、ログレベル、メッセージを含めること
- パスワード、トークン、PII などの機密データをログ出力に**含めてはなりません**

**検証**:
- すべてのサービス/関数のエントリーポイントに設定済みロガーが含まれていること
- 本番コードの主要なログ記録メカニズムとしてアドホックなログ文が使用されていないこと
- ログ設定が出力を一元化されたログサービスにルーティングしていること
- シークレット、トークン、PII がログに記録されていないこと

---

## ルール SECURITY-04: Webアプリケーションの HTTP セキュリティヘッダー (HTTP Security Headers for Web Applications)

**ルール**: 以下の HTTP レスポンスヘッダーは、HTMLを提供するすべてのエンドポイントに設定しなければなりません：

| ヘッダー | 必須値 |
|---|---|
| `Content-Security-Policy` | 制限的なポリシーを定義すること（最低限：`default-src 'self'`） |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY`（フレーミングが必要な場合は `SAMEORIGIN`） |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

**注意**: `X-XSS-Protection` は現代のブラウザでは非推奨です。代わりに `Content-Security-Policy` を使用してください。

**検証**:
- ミドルウェアまたはレスポンスインターセプターが必要なすべてのヘッダーを設定していること
- CSP ポリシーが文書化された正当な理由なしに `unsafe-inline` や `unsafe-eval` を使用していないこと
- HSTS の max-age が少なくとも 31536000（1年）であること

---

## ルール SECURITY-05: すべての APIパラメーターに対する入力検証 (Input Validation on All API Parameters)

**ルール**: すべての APIエンドポイント（REST、GraphQL、gRPC、WebSocket）は処理前にすべての入力パラメーターを検証しなければなりません。検証には以下を**必ず**含めること：
- **型チェック**: 予期しない型を拒否する
- **長さ/サイズ制限**: 文字列の最大長、配列とペイロードの最大サイズを強制する
- **フォーマット検証**: 構造化された入力（メール、日付、ID）に対してアローリスト（正規表現またはスキーマ）を使用する
- **サニタイズ**: XSS を防ぐためにユーザー提供の文字列内のHTML/スクリプトコンテンツをエスケープまたは拒否する
- **インジェクション防止**: すべてのデータベース操作にパラメーター化クエリを使用する（文字列連結は禁止）

**検証**:
- すべての APIハンドラーが検証ライブラリまたはスキーマを使用していること
- 生のユーザー入力がSQL、NoSQL、またはOSコマンドに連結されていないこと
- 文字列入力に明示的な最大長制約があること
- リクエストボディのサイズ制限がフレームワークまたはゲートウェイレベルで設定されていること

---

## ルール SECURITY-06: 最小権限アクセスポリシー (Least-Privilege Access Policies)

**ルール**: すべての IAM ポリシー、ロール、または権限境界は最小権限の原則に従わなければなりません：
- 具体的なリソース識別子を使用する — API がリソースレベルの権限をサポートしない場合を除き、ワイルドカードリソースを使用することは**禁止**（例外は文書化すること）
- 具体的なアクションを使用する — ワイルドカードアクションを使用することは**禁止**
- 可能な限り条件でスコープを絞る
- 読み取りと書き込みの権限を別々のポリシー文に分ける

**検証**:
- 文書化された例外なしにワイルドカードアクションまたはワイルドカードリソースを含むポリシーが存在しないこと
- サービスロールが実際に呼び出す以上の広い権限を持っていないこと
- マネージドポリシーが可能な限りインラインポリシーの代わりに使用されていること
- すべてのロールが特定のサービスまたはアカウントにスコープされた信頼ポリシーを持っていること

---

## ルール SECURITY-07: 制限的なネットワーク設定 (Restrictive Network Configuration)

**ルール**: すべてのネットワーク設定（セキュリティグループ、ネットワーク ACL、ルートテーブル）はデフォルト拒否の原則に従わなければなりません：
- ファイアウォールルール: アプリケーションが必要とする特定のポートのみを開放する
- ポート 80/443 のパブリック向けロードバランサー以外に、送信元 `0.0.0.0/0` のインバウンドルールを設けない
- 明示的な正当性がない限り、すべてのポートに `0.0.0.0/0` のアウトバウンドルールを設けない
- プライベートサブネットには直接のインターネットゲートウェイルートを**設定してはなりません**
- 利用可能な場合はクラウドサービスアクセスにプライベートエンドポイントを使用する

**検証**:
- パブリックロードバランサーの 80/443 以外のポートでインバウンド `0.0.0.0/0` を許可するファイアウォールルールが存在しないこと
- データベースおよびアプリケーションのファイアウォールルールが特定の CIDR ブロックまたはセキュリティグループ参照に制限されていること
- プライベートサブネットが NAT ゲートウェイ（インターネットゲートウェイではない）を経由してルーティングすること
- 高トラフィックのクラウドサービス呼び出しにプライベートエンドポイントが使用されていること

---

## ルール SECURITY-08: アプリケーションレベルのアクセス制御 (Application-Level Access Control)

**ルール**: リソースにアクセスまたは変更するすべてのアプリケーションエンドポイントは、アプリケーション層で認可チェックを実施しなければなりません：
- **デフォルト拒否**: すべてのルート/エンドポイントは、明示的にパブリックとしてマークされない限り認証を必須としなければなりません
- **オブジェクトレベルの認可**: ID でリソースを参照するすべてのリクエストは、リクエストするユーザー/プリンシパルがそのリソースを所有しているか、アクセス権限があるかを検証しなければなりません（IDOR の防止）
- **ファンクションレベルの認可**: 管理者または特権操作は、サーバーサイドで呼び出し元のロール/権限を確認しなければなりません — クライアントサイドの非表示に依存することは禁止
- **CORS ポリシー**: クロスオリジンリソース共有は明示的に許可されたオリジンのみに制限しなければなりません — 認証済みエンドポイントで `Access-Control-Allow-Origin: *` を使用することは禁止
- **トークン検証**: JWT またはセッショントークンはすべてのリクエストでサーバーサイドで検証しなければなりません（署名、有効期限、オーディエンス、発行者）

**検証**:
- すべてのコントローラー/ハンドラーに認可ミドルウェアまたはガードが適用されていること
- リソース ID に対するデータを返すエンドポイントが、呼び出し元の所有権または権限を検証していること
- 管理者/特権ルートにサーバーサイドで明示的なロールチェックが実施されていること
- CORS 設定が認証済みエンドポイントでワイルドカードオリジンを使用していないこと
- トークン検証がすべてのリクエストでサーバーサイドで実行されていること（ログイン時だけでなく）

---

## ルール SECURITY-09: セキュリティハードニングと設定ミスの防止 (Security Hardening and Misconfiguration Prevention)

**ルール**: デプロイされたすべてのコンポーネントはハードニングベースラインに従わなければなりません：
- **デフォルト認証情報の禁止**: デフォルトのユーザー名/パスワードはデプロイ前に変更または無効化しなければなりません
- **最小インストール**: 未使用の機能、フレームワーク、サンプルアプリケーション、およびドキュメントエンドポイントを削除または無効化すること
- **エラーハンドリング**: 本番環境のエラーレスポンスは、スタックトレース、内部パス、フレームワークバージョン、またはデータベース詳細をエンドユーザーに**公開してはなりません**
- **ディレクトリリスティング**: Webサーバーはディレクトリリスティングを**無効にしなければなりません**
- **クラウドストレージ**: クラウドオブジェクトストレージは、明示的に必要とされ文書化されていない限り、パブリックアクセスをブロックしなければなりません
- **パッチ管理**: ランタイム環境、フレームワーク、OSイメージは現在のサポートされているバージョンを使用しなければなりません

**検証**:
- 設定ファイル、環境変数、IaCテンプレートにデフォルト認証情報が存在しないこと
- 本番環境のエラーレスポンスが汎用的なメッセージを返すこと（スタックトレースまたは内部詳細なし）
- 文書化された例外がない限りクラウドオブジェクトストレージのパブリックアクセスがブロックされていること
- サンプル/デモアプリケーションやデフォルトページがデプロイされていないこと
- フレームワークとランタイムのバージョンが現在のものでサポートされていること


---

## ルール SECURITY-10: ソフトウェアサプライチェーンセキュリティ (Software Supply Chain Security)

**ルール**: すべてのプロジェクトはソフトウェアサプライチェーンを管理しなければなりません：
- **依存関係のピン止め**: すべての依存関係は正確なバージョンまたはロックファイルを使用しなければなりません
- **脆弱性スキャン**: 依存関係の脆弱性スキャナーを設定しなければなりません
- **未使用依存関係の禁止**: 積極的に使用されていないパッケージを削除すること
- **信頼できるソースのみ**: 依存関係は公式レジストリまたは検証済みプライベートレジストリからのみ取得しなければなりません — 未確認のサードパーティソースは禁止
- **SBOM**: プロジェクトは本番デプロイメントのソフトウェア部品表 (Software Bill of Materials) を生成しなければなりません
- **CI/CDの完全性**: ビルドパイプラインはピン止めされたツールバージョンと検証済みベースイメージを使用しなければなりません — 本番 Dockerfile や CI 設定での `latest` タグは禁止

**検証**:
- ロックファイルが存在し、バージョン管理にコミットされていること
- CI/CDまたはビルド手順に依存関係の脆弱性スキャンのステップが含まれていること
- 未使用または放棄された依存関係が含まれていないこと
- Dockerfile と CI 設定が本番環境で `latest` またはピン止めされていないイメージタグを使用していないこと
- 依存関係が公式または検証済みレジストリから取得されていること

---

## ルール SECURITY-11: セキュアな設計原則 (Secure Design Principles)

**ルール**: アプリケーション設計は最初からセキュリティを組み込まなければなりません：
- **関心の分離**: セキュリティ上重要なロジック（認証、認可、決済処理）は専用モジュールに分離しなければなりません — コードベース全体に散在させることは禁止
- **多層防御 (Defense in depth)**: 単一の制御が唯一の防衛線であってはなりません — 制御を重ねること（入力検証 + 認可 + 暗号化）
- **レート制限**: パブリック向けエンドポイントは乱用を防ぐためにレート制限またはスロットリングを実装しなければなりません
- **ビジネスロジックの悪用**: 設計は誤用ケースを考慮しなければなりません — ハッピーパスシナリオのみではなく

**検証**:
- セキュリティ上重要なロジックが専用モジュールまたはサービスにカプセル化されていること
- パブリック向けAPIにレート制限が設定されていること
- 設計ドキュメントが少なくとも一つの誤用/悪用シナリオに対処していること

---

## ルール SECURITY-12: 認証と認証情報管理 (Authentication and Credential Management)

**ルール**: ユーザー認証を持つすべてのアプリケーションは以下を実装しなければなりません：
- **パスワードポリシー**: 最低8文字、侵害されたパスワードリストに対するチェック
- **認証情報の保存**: パスワードはアダプティブアルゴリズムを使用してハッシュ化しなければなりません — 弱いまたは非アダプティブなハッシュ化は禁止
- **多要素認証 (MFA)**: 管理者アカウントには MFA が必須で、すべてのユーザーが利用できることが望ましい
- **セッション管理**: セッションはサーバーサイドの有効期限を持ち、ログアウト時に無効化され、secure/httpOnly/sameSite Cookie 属性を使用しなければなりません
- **ブルートフォース保護**: ログインエンドポイントは繰り返しの失敗後にアカウントロックアウト、プログレッシブ遅延、または CAPTCHA を実装しなければなりません
- **ハードコードされた認証情報の禁止**: ソースコードまたは IaC テンプレートにパスワード、APIキー、シークレットを含めない — シークレットマネージャーを使用すること

**検証**:
- パスワードハッシュ化がアダプティブアルゴリズムを使用していること（弱いまたは非アダプティブなハッシュ化は不可）
- セッションCookieに `Secure`、`HttpOnly`、`SameSite` 属性が設定されていること
- ログインエンドポイントにブルートフォース保護（ロックアウト、遅延、またはCAPTCHA）があること
- ソースコードまたは設定ファイルにハードコードされた認証情報が存在しないこと
- 管理者アカウントに MFA がサポートされていること
- セッションがログアウト時に無効化され、定義された有効期限を持つこと

---

## ルール SECURITY-13: ソフトウェアおよびデータの完全性検証 (Software and Data Integrity Verification)

**ルール**: システムはソフトウェアおよびデータの完全性を検証しなければなりません：
- **デシリアライゼーションの安全性**: 信頼されていないデータは検証なしにデシリアライズしてはなりません — 安全なデシリアライゼーションライブラリまたは許可タイプのアローリストを使用すること
- **成果物の完全性**: ダウンロードされた依存関係、プラグイン、およびアップデートはチェックサムまたはデジタル署名で検証しなければなりません
- **CI/CDパイプラインセキュリティ**: ビルドパイプラインはパイプライン定義を変更できる人物を制限しなければなりません — コード作成者とデプロイメント承認者の職務を分離すること
- **CDN と外部リソース**: 外部 CDN から読み込まれるスクリプトやリソースは Subresource Integrity (SRI) ハッシュを使用しなければなりません
- **データ完全性**: 重要なデータ変更は監査可能でなければなりません（誰が、何を、いつ変更したか）

**検証**:
- 信頼されていない入力の安全でないデシリアライゼーションが存在しないこと
- CDN から読み込まれる外部スクリプトに SRI integrity 属性が含まれていること
- CI/CD パイプライン定義がアクセス制御され、変更が監査可能であること
- 重要なデータ変更がアクター、タイムスタンプ、変更前後の値とともにログ記録されていること

---

## ルール SECURITY-14: アラートとモニタリング (Alerting and Monitoring)

**ルール**: ログ記録（SECURITY-02、SECURITY-03）に加え、システムは以下を含まなければなりません：
- **セキュリティイベントのアラート**: 高価値のセキュリティイベントに対してアラートを設定しなければなりません：繰り返しの認証失敗、権限昇格の試み、異常な場所からのアクセス、認可失敗
- **ログの完全性**: ログは追記専用または改ざん防止ストレージに保存しなければなりません — アプリケーションコードは自身の監査ログを削除または変更してはなりません
- **ログ保持**: ログはアプリケーションのコンプライアンス要件に適した最小期間保持しなければなりません（デフォルト：最低90日）
- **モニタリングダッシュボード**: 主要な運用およびセキュリティメトリクスのためのモニタリングダッシュボードまたはアラーム設定を定義しなければなりません

**検証**:
- 認証失敗および認可違反に対してアラートが設定されていること
- アプリケーションのロググループに保持ポリシーが設定されていること（最低90日）
- アプリケーションロールが自身のロググループ/ストリームを削除する権限を持っていないこと
- セキュリティ関連イベント（ログイン失敗、アクセス拒否、権限変更）がアラートを生成すること

## ルール SECURITY-15: 例外処理とフェイルセーフデフォルト (Exception Handling and Fail-Safe Defaults)

**ルール**: すべてのアプリケーションは例外的な条件を安全に処理しなければなりません：
- **キャッチとハンドリング**: すべての外部呼び出し（データベース、API、ファイルI/O）は明示的なエラーハンドリングを持たなければなりません — 本番環境での未処理の Promise rejection や未捕捉例外は禁止
- **フェイルクローズド**: エラー時、システムはアクセスを拒否または操作を停止しなければなりません — フェイルオープンは禁止
- **リソースのクリーンアップ**: エラーパスはリソース（接続、ファイルハンドル、ロック）を解放しなければなりません — try/finally、using ステートメント、または同等のパターンを使用すること
- **ユーザー向けエラー**: ユーザーに表示されるエラーメッセージは汎用的でなければなりません — 内部詳細やシステム情報は含めない
- **グローバルエラーハンドラー**: アプリケーションは未処理の例外をキャッチし、それらをログに記録し（SECURITY-03 に従い）、安全なレスポンスを返すグローバル/トップレベルのエラーハンドラーを持たなければなりません

**検証**:
- すべての外部呼び出し（DB、HTTP、ファイルI/O）に明示的なエラーハンドリングがあること（try/catch、.catch()、エラーコールバック）
- グローバルエラーハンドラーがアプリケーションエントリーポイントに設定されていること
- エラーパスが認可や検証チェックをバイパスしないこと（フェイルクローズド）
- エラーパスでリソースがクリーンアップされること（接続のクローズ、トランザクションのロールバック）
- アプリケーションコードに未処理の Promise rejection や未捕捉例外の警告が存在しないこと

## 適用統合

これらのルールは、すべての AI-DLC ステージに適用される横断的制約です。各ステージにおいて：
- 生成された成果物に対してすべての SECURITY ルールの検証基準を評価する
- ステージ完了サマリーに「セキュリティコンプライアンス」セクションを含め、各ルールを準拠・非準拠・N/A として列挙する
- いずれかのルールが非準拠である場合、それはブロッキングセキュリティ指摘事項となります — 概要で定義されたブロッキング指摘事項の取り扱いに従ってください
- 設計ドキュメントとテスト手順にセキュリティルールの参照を含める
