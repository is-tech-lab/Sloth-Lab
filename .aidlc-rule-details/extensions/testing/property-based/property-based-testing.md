# プロパティベーステスト・ルール (Property-Based Testing Rules)

## 概要

これらのプロパティベーステスト (PBT) ルールは、適用対象の AI-DLC フェーズ全体にわたる横断的制約です。識別可能なプロパティを持つコードが、従来のサンプルベーステストを補完する（置き換えるのではなく）プロパティベースの手法でテストされることを保証します。

プロパティベーステストは、すべての有効な入力に対して成立しなければならない不変条件を定義し、フレームワークを使用してランダムな入力を生成して反例を探します。失敗が見つかった場合、フレームワークは入力を最小の再現ケースにシュリンキング (shrinking) します。このアプローチにより、サンプルベーステストでは見落としがちなエッジケースと微妙なバグを発見できます。

**適用**: 適用対象の各ステージにおいて、モデルはユーザーにステージ完了メッセージを提示する前に、これらのルールへの準拠を検証しなければなりません。

### PBT ブロッキング指摘事項の取り扱い

**ブロッキング PBT 指摘事項**とは以下を意味します：
1. 指摘事項はステージ完了メッセージの「PBT 指摘事項」セクションに、PBT ルールIDと説明とともに**必ず**列挙されなければなりません
2. ステージは、すべてのブロッキング指摘事項が解決されるまで「次のステージに進む」オプションを**提示してはなりません**
3. モデルは「変更を依頼する」オプションのみを提示し、何を変更する必要があるかを明確に説明しなければなりません
4. 指摘事項は、PBT ルールID・説明・ステージのコンテキストとともに `aidlc-docs/audit.md` に**必ず**記録されなければなりません

PBT ルールが現在のプロジェクトまたはユニットに適用されない場合（例：ステートフルコンポーネントが存在しない場合の PBT-06）は、コンプライアンスサマリーに **N/A** として記載してください。これはブロッキング指摘事項にはなりません。

### デフォルトの適用

このドキュメント内のすべてのルールは、デフォルトで**ブロッキング**です。いずれかのルールの検証基準が満たされない場合、それはブロッキング PBT 指摘事項となります — 上記のブロッキング指摘事項の取り扱いに従ってください。

### 部分適用モード

オプトイン (opt-in) 時にユーザーが**部分的**適用を選択した場合、PBT-02、PBT-03、PBT-07、PBT-08、PBT-09 のルールのみが適用されます。その他のルールはアドバイザリー（非ブロッキング）として扱われます。適用モードを `aidlc-docs/aidlc-state.md` の `## Extension Configuration` セクションに記録してください。

### 検証基準のフォーマット

このドキュメント内の検証項目は、コンプライアンスチェックを記述したプレーンな箇条書きです。各項目はレビュー時に「準拠」または「非準拠」として評価される必要があります。

## ルール PBT-01: 設計時のプロパティ識別 (Property Identification During Design)

**ルール**: ビジネスロジック、データ変換、またはアルゴリズム操作を含むすべてのユニットは、機能設計 (Functional Design) ステージ中にテスト可能なプロパティを分析しなければなりません。分析では、以下のプロパティカテゴリーのどれが適用されるかを**必ず**特定してください：

| カテゴリー | 説明 | 例 |
|---|---|---|
| ラウンドトリップ (Round-trip) | 逆操作と組み合わせると元の値が得られる操作 | serialize → deserialize = identity |
| 不変条件 (Invariant) | 変換が何らかの測定可能な特性を保持する | sort はコレクションのサイズと要素を保持する |
| 冪等性 (Idempotence) | 操作を2回適用しても1回と同じ結果が得られる | dedup(dedup(list)) = dedup(list) |
| 可換性 (Commutativity) | 異なる操作の順序が同じ結果を生む | add(a, b) = add(b, a) |
| オラクル (Oracle) | 参照実装または単純化したモデルで結果を検証できる | 最適化アルゴリズム vs ブルートフォース |
| 帰納 (Induction) | より小さな入力に対して証明されたプロパティがより大きな入力にも拡張される | 再帰的構造、分割統治法 |
| 検証の容易性 (Easy verification) | 計算は困難だが確認は容易な結果 | 迷路ソルバーの出力を歩いて検証できる |

識別されたプロパティはユニットの機能設計成果物に**必ず**文書化され、PBT テスト要件としてコード生成に引き継がれなければなりません。

**検証**:
- 機能設計成果物にコンポーネントごとの識別済みプロパティを列挙した「テスト可能なプロパティ」セクションが含まれていること
- 各識別済みプロパティが上記のカテゴリーの1つを参照していること
- 識別可能なプロパティがないコンポーネントは「PBT プロパティなし」と明示され、簡潔な根拠が記載されていること
- プロパティリストがコード生成計画時に参照されていること

## ルール PBT-02: ラウンドトリッププロパティ (Round-Trip Properties)

**ルール**: 論理的な逆操作を持つすべての操作は、ラウンドトリップを検証するプロパティベーステストを持たなければなりません。これには以下が含まれますが、これに限りません：
- シリアライゼーション / デシリアライゼーション（JSON、XML、Protobuf、バイナリフォーマット）
- エンコーディング / デコーディング（Base64、URLエンコーディング、圧縮）
- パーシング / フォーマット（日付パーシング、数値フォーマット、構造化入力によるテンプレートレンダリング）
- 暗号化 / 復号化（キーが利用可能な場合）
- データベース書き込み / 読み取り（I/O 自体ではなくデータ変換レイヤー向け）
- すべての有効な `x` に対して `f_inverse(f(x)) = x` となる関数ペア

プロパティベーステストは、ドメインに適したジェネレーター（PBT-07 参照）を使用してランダムな有効入力を生成し、ラウンドトリップが元の入力と等しい値を生成することをアサートしなければなりません。

**検証**:
- すべてのシリアライゼーション/デシリアライゼーションペアにラウンドトリッププロパティテストがあること
- すべてのエンコーディング/デコーディングペアにラウンドトリッププロパティテストがあること
- すべてのパーシング/フォーマットペアにラウンドトリッププロパティテストがあること（または変換が非可逆である理由を文書化していること）
- ラウンドトリップテストがハードコードされた例ではなく生成された入力を使用していること
- 非可逆変換（例：精度損失を伴う浮動小数点フォーマット）が許容偏差を文書化し、許容範囲内でテストしていること

## ルール PBT-03: 不変条件プロパティ (Invariant Properties)

**ルール**: 文書化された不変条件を持つ関数は、生成された入力にわたってそれらの不変条件が成立することを検証するプロパティベーステストを持たなければなりません。一般的な不変条件には以下が含まれます：
- **サイズ保持**: 出力コレクションが入力と同じサイズを持つ（例：map、sort）
- **要素保持**: 出力が入力とまったく同じ要素を含む（順序が変わる場合がある）（例：sort、shuffle）
- **順序保証**: 出力が順序制約を満たす（例：sort は非減少順序を生成する）
- **範囲制約**: 出力値が定義された範囲内に収まる（例：normalize は [0, 1] の値を生成する）
- **型保持**: 出力型がすべての有効な入力に対して期待される型と一致する
- **ビジネスルールの不変条件**: 常に成立しなければならないドメイン固有のルール（例：「有効なトランザクション後に口座残高がマイナスにならない」、「割引が商品価格を超えない」）

**検証**:
- 各文書化された不変条件に対応するプロパティベーステストがあること
- 不変条件テストが境界値を含む幅広い入力を生成していること
- 機能設計で識別されたビジネスルールの不変条件が PBT でカバーされていること
- 不変条件テストがサンプルベーステストの正確なアサーションを重複させないこと — 特定のケースではなく一般的なルールをテストすること

---

## ルール PBT-04: 冪等性プロパティ (Idempotency Properties)

**ルール**: 冪等性を主張または要求するすべての操作は、それを証明するプロパティベーステストを持たなければなりません。テストは、すべての有効な生成入力に対して `f(f(x)) = f(x)` であることを検証しなければなりません。これは以下に適用されます：
- 冪等として文書化された APIエンドポイント（PUT、DELETE）
- データの正規化またはサニタイズ関数
- キャッシュ投入操作
- 重複排除ロジック
- 設定適用（設定を2回適用しても状態が変わらないこと）
- 少なくとも1回の配信システムでのメッセージ処理

**検証**:
- 冪等として文書化されたすべての操作が `f(f(x)) = f(x)` をアサートする PBT を持っていること
- 冪等性テストがドメインに適したジェネレーター（プリミティブ型のみでなく）を使用していること
- ステートフルな操作について、テストが単一適用と繰り返し適用後の観察可能な状態の等価性を検証していること

---

## ルール PBT-05: オラクルおよびモデルベーステスト (Oracle and Model-Based Testing)

**ルール**: 参照実装、単純化したモデル、または既知の正しいアルゴリズムが存在する場合、プロパティベーステストはテスト対象システムをオラクルと比較しなければなりません。これは以下に適用されます：
- 既知のブルートフォース版を置き換える最適化アルゴリズム
- レガシー実装を置き換えるリファクタリングされたコード
- 順次バージョンと比較した並列/並行実装
- 既知のアルゴリズムのカスタム実装（ソート、検索、グラフ探索）
- 参照データベースと比較した新しいクエリエンジン

プロパティベーステストはランダムな有効入力を生成し、テスト対象システムがすべての生成入力に対してオラクルと同等の結果を生成することをアサートしなければなりません。

**検証**:
- 参照実装が存在する（または簡単に記述できる）場合、オラクル PBT が存在すること
- オラクルテストが通常、境界、および敵対的ケースをカバーする多様な入力を生成していること
- 等価性が正確に定義されていること（完全な等値、構造的等価、または文書化された許容誤差）
- オラクルが存在しない場合、このルールは根拠とともに N/A とマークされること

---

## ルール PBT-06: ステートフルプロパティテスト (Stateful Property Testing)

**ルール**: 可変状態を管理するコンポーネントはステートフルプロパティテストのために評価されなければなりません。ステートフル PBT はシステムに対してランダムなコマンド（操作）のシーケンスを生成し、各ステップ後に不変条件が成立することを検証します。これは以下に適用されます：
- インメモリキャッシュとデータストア
- ステートマシンとワークフローエンジン
- キューとバッファの実装
- セッション管理システム
- ショッピングカート、注文パイプライン、および類似のステートフルビジネスオブジェクト
- 操作の結果が以前の操作に依存するコンポーネント

ステートフル PBT は以下を**必ず**行わなければなりません：
- テスト対象システムをミラーリングする単純化したモデル（参照状態）を定義する
- 有効なコマンドのランダムシーケンスを生成する（追加、削除、更新、クエリなど）
- 実際のシステムとモデルの両方に対して各コマンドを実行する
- 各コマンド後にシステムとモデルの間で観察可能な状態またはクエリ結果が一致することをアサートする
- 空のシーケンスを含む様々な長さのシーケンスをテストする

**検証**:
- 機能設計で識別されたステートフルコンポーネントにステートフル PBT があるか、または適用できない理由を文書化していること
- 比較のための単純化したモデルが定義されていること
- コマンドジェネレーターが現実的なパラメーター分布で有効な操作シーケンスを生成していること
- 不変条件がシーケンスの最後だけでなく各コマンド後に確認されていること
- ステートフルコンポーネントが存在しない場合、このルールは N/A とマークされること

---

## ルール PBT-07: ジェネレーターの品質 (Generator Quality)

**ルール**: プロパティベーステストは、単なるプリミティブ型ではなく、現実的で構造化された入力を生成するドメイン固有のジェネレーターを使用しなければなりません。不適切なジェネレーター（例：メールフィールドにランダム文字列、年齢フィールドに無制限の整数）は意味のないテストケースを生成し、実際のバグを見逃します。

ジェネレーター要件：
- **ドメイン型**: ビジネス制約（有効なメールフォーマット、正の金額、有効な日付範囲）を尊重するドメインオブジェクト（例：User、Order、Transaction）のカスタムジェネレーターを**必ず**作成すること
- **制約付きプリミティブ**: 数値ジェネレーターはドメインが要求する場合、現実的な範囲に**必ず**制約すること
- **構造化データ**: 複雑な入力（ネストされたオブジェクト、ドメインオブジェクトのリスト）のジェネレーターは構造的に有効なデータを**必ず**生成すること
- **エッジケースの包含**: ジェネレーターは通常の値とともに境界値（空のコレクション、ゼロ、最大値、Unicode文字列）を含むように設定すべきです
- **再利用性**: ドメインジェネレーターはテストファイル間で重複させずに再利用可能なテストユーティリティとして定義すべきです

**検証**:
- ドメイン型パラメーターに生のプリミティブジェネレーターのみ（例：`st.integers()` のみ）を使用している PBT が存在しないこと
- PBT で使用されるドメインオブジェクトにカスタムジェネレーターが存在すること
- ジェネレーターが文書化されたビジネス制約を尊重していること（例：正の金額、有効なフォーマット）
- 複数のテストが同じドメイン型を共有する場合、ジェネレーター定義が集約されて再利用可能であること

---

## ルール PBT-08: シュリンキングと再現性 (Shrinking and Reproducibility)

**ルール**: すべてのプロパティベーステストはシュリンキング (shrinking) と決定論的な再現性をサポートしなければなりません。

- **シュリンキング**: プロパティが失敗した場合、PBT フレームワークは失敗した入力を最小の再現ケースに**自動的に**縮小しなければなりません。テストは、文書化された技術的な理由（例：シュリンキングが統合テストの外部サービス呼び出しと互換性がない）がない限り、フレームワークのシュリンキングメカニズムを無効化または迂回してはなりません。
- **再現性**: すべての PBT 実行はシード値によって再現可能でなければなりません。シードは失敗時にログに記録され、正確な失敗シナリオを再現できなければなりません。CI 設定は決定論的な実行のために固定シードを使用するか、失敗後の再現のためにすべての実行でランダムシードをログに記録しなければなりません。
- **CI統合**: PBT はプロジェクトの CI パイプラインに**必ず**含めなければなりません。不安定な PBT 失敗（コード変更なしで再試行すると成功するテスト）は抑制せずに調査しなければなりません。

**検証**:
- PBT フレームワークのシュリンキングが有効になっていること（オーバーライドまたは無効化されていないこと）
- 失敗時のテスト出力にシード値と縮小された最小失敗入力が含まれていること
- CI 設定がすべての PBT 実行でシードをログに記録するか、固定シードを使用していること
- 文書化された正当性なしに CI から除外された PBT が存在しないこと
- 不安定な PBT 失敗が追跡・調査されており、サイレントに再試行されていないこと

---

## ルール PBT-09: フレームワーク選定 (Framework Selection)

**ルール**: プロジェクトはその主要言語に適切なプロパティベーステストフレームワークを選定して設定しなければなりません。フレームワークは以下をサポートしなければなりません：
- ドメイン型のカスタムジェネレーター/ストラテジー
- 失敗ケースの自動シュリンキング
- シードベースの再現性
- プロジェクトの既存テストランナーとの統合

言語別推奨フレームワーク（非網羅的）：

| 言語 | フレームワーク | 備考 |
|---|---|---|
| Python | Hypothesis | 成熟度が高く、優れたシュリンキング、Django統合 |
| JavaScript / TypeScript | fast-check | Jest、Vitest、Mocha と統合 |
| Java | jqwik | JUnit 5 統合、ステートフルテストサポート |
| Kotlin | Kotest Property Testing | Kotest フレームワーク統合 |
| Scala | ScalaCheck | SBT 統合、広く採用されている |
| Rust | proptest | マクロベース、優れたシュリンキング |
| Go | rapid | 軽量、慣用的な Go |
| Haskell | QuickCheck | オリジナルの PBT フレームワーク |
| C# / .NET | FsCheck | xUnit、NUnit と動作 |
| Erlang / Elixir | PropEr / StreamData | OTP 対応、ステートフルテスト |

選定されたフレームワークはテックスタックの決定事項に文書化され、プロジェクトの依存関係として含めなければなりません。

**検証**:
- PBT フレームワークが選定されてテックスタックの決定事項に文書化されていること
- フレームワークがプロジェクトの依存関係に含まれていること（package.json、pom.xml、requirements.txt など）
- フレームワークがカスタムジェネレーター、シュリンキング、シードベースの再現性をサポートしていること
- プロジェクトが複数の言語を使用する場合、PBT 適用可能なコードを持つ各言語でフレームワークが選定されていること

## ルール PBT-10: 補完的テスト戦略 (Complementary Testing Strategy)

**ルール**: プロパティベーステストはサンプルベーステストを補完しなければならず、置き換えてはなりません。両アプローチは異なる目的を果たします：

- **サンプルベーステスト**: 明示的な期待値を持つ具体的な既知シナリオ、回帰ケース、およびビジネス上重要なエッジケースを文書化します。具体的な振る舞いの実行可能なドキュメントとして機能します。
- **プロパティベーステスト**: 広い入力空間にわたる一般的な不変条件を検証します。未知のエッジケースを見つけ、プロパティが普遍的に成立することを検証します。

要件：
- ユーザーストーリーまたは要件で識別された重要なビジネスシナリオは、PBT が同じプロパティをカバーしている場合でも、明示的なサンプルベーステストを**必ず**持たなければなりません
- PBT はビジネス上重要なパスの唯一のテストであってはなりません — 少なくとも1つのサンプルベーステストが主要シナリオの期待される振る舞いを固定しなければなりません
- PBT が失敗ケースを発見した場合、縮小された最小例を永続的なサンプルベース回帰テストとして追加すべきです
- テストドキュメントはサンプルベーステストとプロパティベーステストを明確に区別しなければなりません（別テストファイル、テストクラス、または明確に命名されたテスト関数）

**検証**:
- ビジネス上重要なパスにサンプルベーステストとプロパティベーステストの両方があること
- PBT が重要な機能の唯一のテストカバレッジとして使用されていないこと
- テストファイルまたはテストクラスが PBT とサンプルベーステストを明確に分離または表示していること
- PBT で発見された失敗からの回帰テストが永続的なサンプルベーステストとして記録されていること

---

## 適用統合

これらのルールは以下の AI-DLC ステージに適用される横断的制約です：

| ステージ | 適用ルール | 適用内容 |
|---|---|---|
| 機能設計 (Functional Design) | PBT-01 | プロパティ識別が設計成果物に含まれていなければならない |
| NFR要件 (NFR Requirements) | PBT-09 | フレームワーク選定がテックスタックの決定事項に含まれていなければならない |
| コード生成 - 計画 (Code Generation Planning) | PBT-01〜PBT-10 | コード生成計画に識別されたプロパティの PBT テストステップが含まれていなければならない |
| コード生成 - 生成 (Code Generation Generation) | PBT-02〜PBT-08、PBT-10 | 生成されたテストにサンプルベーステストと並んで PBT が含まれていなければならない |
| ビルドとテスト (Build and Test) | PBT-08 | テスト実行手順にシードログと CI 統合を含む PBT が含まれていなければならない |

適用対象の各ステージにおいて：
- 生成された成果物に対してすべての PBT ルールの検証基準を評価する
- ステージ完了サマリーに「PBT コンプライアンス」セクションを含め、各ルールを準拠・非準拠・N/A として列挙する
- いずれかのルールが非準拠である場合、それはブロッキング PBT 指摘事項となります — 概要で定義されたブロッキング指摘事項の取り扱いに従ってください
- 設計ドキュメントとテスト手順に PBT ルールの参照を含める

## 付録: プロパティカテゴリー・クイックリファレンス

機能設計 (PBT-01) 時にプロパティを識別する開発者と AIモデル向け：

| パターン名 | 正式用語 | テスト形式 | 使用場面 |
|---|---|---|---|
| 行って帰ってくる (There and back again) | 可逆関数 (Invertible function) | `f_inv(f(x)) == x` | シリアライゼーション、エンコーディング、パーシング |
| 変わらないもの (Some things never change) | 不変条件 (Invariant) | `measure(f(x)) == measure(x)` | ソート、マップ、フィルター、変換 |
| 変われば変わるほど同じ (The more things change, the more they stay the same) | 冪等性 (Idempotence) | `f(f(x)) == f(x)` | 正規化、重複排除、キャッシュ書き込み |
| 異なる道、同じ目的地 (Different paths, same destination) | 可換性 (Commutativity) | `f(g(x)) == g(f(x))` | 算術演算、集合操作、独立した変換 |
| まず小さな問題を解く (Solve a smaller problem first) | 構造的帰納 (Structural induction) | `x` のプロパティが `x + 要素` にも成立する | 再帰的構造、リスト、ツリー |
| 証明は難しいが検証は簡単 (Hard to prove, easy to verify) | 検証 (Verification) | `verify(solve(x)) == true` | ソルバー、オプティマイザー、検索アルゴリズム |
| テストオラクル (The test oracle) | 参照比較 (Reference comparison) | `f(x) == oracle(x)` | 最適化 vs ブルートフォース、リファクタリング vs レガシー |

出典：Scott Wlaschin 氏の「Choosing properties for property-based testing」([fsharpforfunandprofit.com](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)) から採用されたプロパティカテゴリー分類。
