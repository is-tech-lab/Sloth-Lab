# Sloth-Lab 要件確認の質問

グリーンフィールド (Greenfield) プロジェクトとして検出されました。  
以下の質問に回答することで、最適な開発計画を立てることができます。  
各質問の `[Answer]:` タグの後にアルファベットの選択肢を記入してください。

---

## 質問 1
Sloth-Lab では何を作りますか？プロジェクトの概要を教えてください。

A) Webアプリケーション（ブラウザで使うもの）
B) モバイルアプリ（iOS / Android）
C) バックエンドAPI / マイクロサービス
D) CLIツール / スクリプト
E) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: B
ホーム画面常駐ウィジェット（iOS / Android）＋位置情報集約バックエンドの構成。ウィジェットAPIを使うためネイティブモバイルアプリが前提。

## 質問 2
このプロジェクトの主要な機能・解決したい問題は何ですか？（自由記述でも可）

A) 情報管理・一覧表示（リスト、カタログ、ダッシュボードなど）
B) コミュニケーション・コラボレーション（チャット、通知、共有など）
C) データ処理・変換・分析（集計、可視化、AIなど）
D) エンターテイメント・ゲーム・体験
E) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: E
D（体験）＋B（通知・近接検知）の複合。「だるい」タップで半径3km以内の同志数を取得しキャラが増殖するウィジェット体験が中核。解決課題は「孤立した罪悪感の即時解消」と「他者の怠惰の可視化」。

想定するユーザーは誰ですか？

A) ハッカソン審査員・デモ参加者のみ（プロトタイプ・PoC）
B) 社内ユーザー・チームメンバー
C) 一般消費者（不特定多数のエンドユーザー）

## 質問 4
使用する技術スタック（フロントエンド）を教えてください。

A) React / Next.js
B) Vue.js / Nuxt.js
C) プレーンHTML / JavaScript
D) フロントエンドなし（API のみ）
E) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: E
iOS：Swift（WidgetKit）/ Android：Kotlin（Glance Widget）。ウィジェット常駐が核心機能のため、ネイティブウィジェットAPIが必須。ハッカソンのスコープ次第でReact Nativeも選択肢（WidgetKitネイティブ拡張との組み合わせ）。

A) Node.js / TypeScript

C) Java / Kotlin（Spring Boot など）

## 質問 6
データの永続化はどうしますか？

A) リレーショナルDB（PostgreSQL / MySQL など）
B) NoSQL（MongoDB / DynamoDB / Firebase など）
C) インメモリ / ファイルベース（SQLite、JSON など）
D) データ永続化なし
E) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: B
DynamoDB（AWS）。ユーザーの位置情報・タップイベント・タイムスタンプをリアルタイムで書き込み・集計するユースケースに最適。将来の「怠惰ヒートマップ」データ資産化にも対応しやすい。

AIやLLM（大規模言語モデル）を活用しますか？

A) はい、中核機能として使用する（Claude、OpenAI など）

C) いいえ、AI/LLMは使用しない

## 拡張機能 — セキュリティ (Security Extension)
このプロジェクトにセキュリティルールを強制適用しますか？

A) はい — すべてのSECURITYルールをブロッキング制約として適用する（本番グレードのアプリに推奨）
B) いいえ — SECURITYルールをスキップする（PoC、プロトタイプ、実験的プロジェクトに適切）
X) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: B
ハッカソンPoCのため、まずはB（スキップ）で開発速度を優先する。ただしGPS位置情報はプライバシーセンシティブなデータのため、本番移行時には位置情報の精度丸め・同意フロー・データ保持期間の設計が必要になる点を留意する。

## 拡張機能 — プロパティベーステスト (Property-Based Testing Extension)
このプロジェクトにプロパティベーステスト (PBT) ルールを適用しますか？

A) はい — すべてのPBTルールをブロッキング制約として適用する（ビジネスロジック、データ変換、シリアライゼーション、ステートフルなコンポーネントを持つプロジェクトに推奨）
B) 部分適用 — 純粋関数とシリアライゼーションのラウンドトリップにのみPBTルールを適用する（限られたアルゴリズム的複雑さを持つプロジェクトに適切）
C) いいえ — すべてのPBTルールをスキップする（シンプルなCRUDアプリ、UIのみのプロジェクト、重要なビジネスロジックのない薄い統合レイヤーに適切）
X) その他 (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: C
バックエンドは「位置情報を受け取り→半径内のユーザー数を返す」というシンプルなAPIであり、複雑なビジネスロジックや変換ロジックは存在しない。PBTの恩恵が薄いためスキップ。
