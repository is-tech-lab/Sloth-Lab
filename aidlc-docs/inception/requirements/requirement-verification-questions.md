### 質問 6: AIナマケモノの人格設計を要件として明文化するか？

AIナマケモノは「動的IPの本体」と位置づけているが、`requirements.md` にはトーン・口調・人格制約が明文化されていない。System Prompt で固定されるべき要件として記述するか？

A) FR-010 として新規追加。トーン・思想立場・口調・拒絶しない・比較しないなどの属性を System Prompt 固定として要件化
B) 実装詳細として Application Design に委譲

[Answer]: A

- トーン: 優しいが断定的、説教しない
- 思想立場: ダメ・怠惰を肯定、労働至上主義に静かに抵抗

## Section 3-A: 技術スタック検証（Stage 2 中の追加質問）

### 質問 9: Claude API 呼び出しを Bedrock 経由に変更するか？

`requirements.md` の技術スタックは「Claude API (Anthropic)」（Anthropic 直 API、`@anthropic-ai/sdk`、`ANTHROPIC_API_KEY` 認証）として記述されていた。AWS インフラ（DynamoDB）と一体運用するなら Amazon Bedrock 経由に統一する選択肢がある。どうするか？

A) **Amazon Bedrock 経由の Claude に統一**：`@aws-sdk/client-bedrock-runtime` 利用、IAM 認証、AWS リージョン管理に統合
B) Anthropic 直 API を維持（既存記述のまま）
C) ハイブリッド（環境別に使い分け）
D) Other (`[Answer]:` タグの後に記述)

[Answer]: A

**実施内容**:
- 技術スタック表を「Amazon Bedrock 経由の Claude（Anthropic 提供モデル）」に書き換え
- AI 呼び出し SDK 行を新設：「AWS SDK for JavaScript v3（`@aws-sdk/client-bedrock-runtime`）」
- インフラ行に「DynamoDB / Bedrock / IAM 一体運用」を追記
- 注記に「AI 呼び出しは Anthropic 直 API ではなく Amazon Bedrock 経由に統一（AWS 環境で完結、IAM ベース認証、ベンダーロックイン回避、AWS インフラとの一体管理）」を追加
- FR-002・NFR-001・NFR-007 の API 呼び出し記述を Bedrock 系に統一
- application-design 配下（components / services / methods / dependency / unit-of-work / unit-of-work-dependency）の依存関係・環境変数・呼び出し記述を全面更新
  - 環境変数：`ANTHROPIC_API_KEY` 削除 → `BEDROCK_MODEL_ID` 追加・`AWS_REGION`（既存）流用・IAM ロール推奨
  - SDK：`@anthropic-ai/sdk` → `@aws-sdk/client-bedrock-runtime`
- ideation/ideas.md・plans/execution-plan.md の技術記述も統一
- 1回目サイクル `requirements-questions.md` 質問3（当時 A) Claude API）に対し、3回目サイクルで上書きされた旨を冒頭に注釈追記
- audit.md に変更経緯を記録

**変更理由**:
- AWS インフラ（DynamoDB）と認証基盤を統合（IAM）し、API キー管理コストを削減
- AWS リージョン障害時のフェイルオーバー設計を統一できる
- Bedrock のモデル切り替え（Claude → 他社モデル）の可逆性
- AWS 環境で完結することでネットワーク経路の単純化・データ越境リスクの回避

### 質問 10: RAG 引用ライブラリを除外し、引用ソース戦略を再定義するか？

`requirements.md` FR-007 は当初「RAG 引用ライブラリ（5経路紐付け）」として、偉人・哲学・科学・統計の出典を**RAG（検索拡張生成）**で管理する設計だった。AWS インフラの選定（Bedrock）と PoC のシンプルさを優先するなら、別の戦略がある。どうするか？

A) **PoC は LLM の学習済み知識を信用、Phase 2 で S3 + Agentic Search**：RAG（ベクトル検索）を採用せず、PoC では Bedrock Claude の事前学習を信用（ハルシネーションリスク受容）。Phase 2 で S3 に引用源を配置し、Bedrock Agents または tool use で Agentic Search 実装
B) RAG（ベクトル検索）を維持
C) 引用機能そのものを廃止
D) Other (`[Answer]:` タグの後に記述)

[Answer]: A

**実施内容**:
- **FR-007 を「引用ソース戦略」に再定義**：

  - 想定引用源マッピング表は維持（PoC ではプロンプトのヒント、Phase 2 では S3 検索対象）
  - PoC 実装ロジックと Phase 2 実装ロジックを分けて明記
- **FR-003**: 引用源の取り扱いに「PoC では LLM の学習済み知識を信用」「Phase 2 で S3 + Agentic Search」を追記
- **NFR-005**: ハルシネーション対策の記述を「PoC では LLM 自体に委ねる、Phase 2 で S3 + Agentic Search で事実検証」に変更
- **PoC MVP 除外表**: 「RAG / S3 + Agentic Search による引用検証」を Phase 2 として明示
- **シナリオ1A/1B**: 引用生成を「LLM の学習済み知識から」と明記
- **成功基準**: 引用付き生成のチェックに「PoC では LLM の学習済み知識を信用」を追記
- **application-design 配下**：
  - `lib/rag/citations.json` / `lib/rag/retriever.ts` を**削除**（ディレクトリツリーから除外）
  - `RAGRetriever` コンポーネントを**削除**
  - AINamakemonoService の依存から RAGRetriever を削除、UserHistory のみに
  - サービス記述を「LLM の学習済み知識から引用生成」に書き換え
  - サンドイッチフロー図から `RAGRetriever.search` を削除し、「プロンプト構築（5経路言語化テンプレ + 想定引用源ヒント）」に置換
  - Phase 2 構想として S3 + Agentic Search を services.md に注記
- **unit-of-work.md**: Unit 2 の生成ファイルから `lib/rag/` を除外、コード整理戦略の表からも削除、Phase 2 で `lib/agents/` 追加予定と注記

**変更理由**:
- PoC のシンプルさを優先：外部ナレッジベース構築・ベクトル化・チャンク分割の複雑性を回避
- 5経路 × ナマケモノ人格 × 動的IPの体験設計の検証に集中
