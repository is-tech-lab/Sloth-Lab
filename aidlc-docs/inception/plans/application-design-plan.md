## 質問 1: バックエンドのアーキテクチャパターン

Node.js/TypeScript バックエンドの内部構造として、どのパターンを採用しますか？

A) **レイヤードアーキテクチャ（Controllers / Services / Repositories）** — 3層構造。Controller がリクエスト処理、Service がビジネスロジック、Repository がDB操作を担当
   - 最も一般的なNode.jsパターン。コードが予測しやすく、チーム全員に理解しやすい
   - 例: `AuthController → AuthService → UserRepository`

B) **クリーンアーキテクチャ** — UseCase / Repository インターフェースで依存性を逆転させる。テスト容易性が高い
   - MVPには過剰設計になりやすいが、長期メンテを重視する場合に有効

C) **シンプルルーター構成** — Express/Fastify のルーターに直接ロジックを書く。MVPの速度優先
   - テストしにくいが、最初のデモ品質を最速で達成できる

D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: D。ドメイン駆動にしたいので、Domain, Usecase, Repository, Presenterの各レイヤーで実装をお願いします。

## 質問 2: AI変換パイプラインの配置

GPT-4V → DALL-E 3 の変換パイプラインをどこに配置しますか？

A) **メインバックエンドに統合** — Backend API サーバー内に AI変換エンドポイントを含める（単一サービス）
   - シンプルで管理しやすい。デプロイが1つ。ただしAI処理が重いとバックエンド全体に影響する可能性

B) **独立した Lambda 関数** — AI変換専用の Lambda 関数として分離。バックエンドからこの Lambda を呼び出す
   - AI処理の独立したスケーリングが可能。コールドスタートのリスクあり

C) **独立した別サービス（ECS等）** — AI変換専用の常時起動サービスとして分離
   - 安定した応答速度。コスト高め

D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: C。「短期」と言うダメポイントを解消するにはスピーディーに処理が行われる必要があるので、インフラ側で独立させたいです。AIの画像処理が重いとバックエンド全体に影響する可能性もありますしね。

## 質問 3: バックエンドのランタイム構成

バックエンドAPIのAWS実行環境を選んでください（requirements.md では未決定でした）。

A) **AWS Lambda（サーバーレス）** — リクエストごとに起動。スケーリング自動。コストが従量課金
   - コールドスタートがある（Node.js Lambdaは通常500ms〜1秒）。API GatewayまたはALBと組み合わせる

B) **AWS ECS（Fargate）** — コンテナを常時起動。レスポンスが安定。コストは固定的
   - コールドスタートなし。フィードの3秒以内目標を安定して達成しやすい

C) **AWS App Runner** — コンテナを自動デプロイ・スケーリング。ECSより運用が簡単
   - ECSとLambdaの中間的な選択肢

D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: B。「短期」と言うダメポイントを解消するにはスピーディーに処理が行われる必要があります。コストが多少上がってもこの安定性は保ちたいです。

## 質問 4: 画像アップロードフロー

before/after画像をS3にアップロードする方式を選んでください。

A) **Presigned URL 方式（推奨）** — バックエンドがS3のPresigned URLを発行 → モバイルがそのURLに直接アップロード
   - バックエンドに画像データが流れないため高速。サーバー帯域を使わない
   - フロー: Mobile → Backend (URL発行) → Mobile → S3 直接アップロード

B) **バックエンド経由** — モバイルがバックエンドに画像を送信 → バックエンドがS3に転送
   - シンプルだがバックエンドのメモリ・帯域を使う。5秒以内の画像アップロード目標に影響する可能性

C) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: A

## 質問 5: モバイルアプリの状態管理

React Native アプリのグローバル状態管理として何を採用しますか？

A) **Zustand** — 軽量シンプルな状態管理ライブラリ。ボイラープレートが少ない。MVPに適している
   - 最近のReact Nativeプロジェクトで採用が増えている

B) **Redux Toolkit** — 業界標準の状態管理。デバッグツールが充実。構造が明確
   - セットアップコストが高め。MVPには過剰になる可能性がある

C) **React Context + useState** — 追加ライブラリなし。シンプルな構成
   - 規模が大きくなるとパフォーマンスの問題が出やすい

D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: A。フロントエンドのことは詳しくないので後で修正が入るかもしれませんが、一旦Aでお願いします。

## 質問 6: モバイルのAPIクライアント

バックエンドAPIとの通信に使うHTTPクライアントを選んでください。

A) **Axios + カスタムAPIクライアント層** — Axiosで薄いラッパークラスを作成。JWTトークンをインターセプターで自動付与
   - 最も一般的な選択。テストしやすい

B) **TanStack Query（React Query）+ Axios** — データフェッチ・キャッシュ・ローディング状態管理を自動化
   - フィードのキャッシュやいいね後の再フェッチを宣言的に書ける。学習コストあり

C) **組み込みfetch + カスタムフック** — 追加ライブラリなし。標準fetchAPIで実装
   - 依存を最小化できる。エラーハンドリングは自前で実装が必要

D) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: A

## 質問 7: モバイルのナビゲーション構造

React Native のナビゲーション構造として何を採用しますか？

A) **React Navigation（Stack + Tab）** — 業界標準ライブラリ。Stack Navigator + Bottom Tab Navigatorの組み合わせ
   - 認証フロー（Stack）とメインアプリ（Tab: フィード・カメラ・マイページ）を分離できる

B) **Expo Router（ファイルベースルーティング）** — Next.js的なファイルシステムベースのルーティング
   - Expoプロジェクトとの相性が良い。Next.jsに慣れている場合に直感的

C) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: A

## 質問 8: データベースアクセス層（バックエンド）

Node.js/TypeScriptからPostgreSQLにアクセスする方法を選んでください。

A) **Prisma ORM** — 型安全なクエリ。スキーマ定義からTypeScript型を自動生成。マイグレーション管理も統合
   - 最も生産性が高い。RTWのような新規プロジェクトに最適

B) **Drizzle ORM** — 軽量でSQLライクな書き方。Prismaより学習コストが低い場合もある
   - 比較的新しいが採用が増加中

C) **Knex.js（クエリビルダー）** — ORMではなくクエリビルダー。SQLに近い制御が可能

D) **生SQL（pg ドライバー直接）** — 最も細かい制御が可能。型安全性は自前で担保

E) Other (その他の場合は [Answer]: タグの後に記述してください)

[Answer]: A。今回は画像の処理(GPT-4V → DALL-E 3 の変換パイプライン)をインフラ側(ECS)で独立でサーバーを立てます。これは処理のスピードを意識した設計なためです。そして、このサービスはAIの私処理とその投稿への反応がコアです。そのため、MVP段階でデータベースアクセスが頻繁に発生することはほとんどないので最もシンプルなもので良いです。MVP以降はポイント付与や企業ダッシュボードのためにDBへのアクセスが増える想定なので、本番やMVPの拡張度次第では変更になるかもしれませんが、一旦これでいいです。
